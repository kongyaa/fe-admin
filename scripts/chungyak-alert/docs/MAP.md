# 분양 예정 지도

서울 재개발·재건축과 경기 공공주택지구가 언제쯤 분양할지 거칠게 보여 주는 공개 정적 사이트다.
예상 시기는 단계별 경험 규칙으로 잡은 추정이며, 실제 일정이 아니다.

## 파이프라인

`src/pipeline/build-map.js`가 `site/projects.json`을 만들고(커밋하지 않음), `site/`의 정적 페이지가 그 파일을 읽는다.

1. 서울: `seoul-redevelop.js`가 서울 열린데이터광장 OA-22856 페이지에서 기준월이 가장 늦은 xlsx를 골라 내려받고, 사업 하나씩 지도 형태로 바꾼다. 형식은 `docs/sources.md`의 `서울시 정비사업 추진현황` 참고.
2. 공공주택지구: `newtowns.js`가 `data/newtowns.yaml`을 읽고 검사한다.
3. 예상 시기: `expected-window.js`가 단계와 단계 날짜로 기간을 잡고, 기간 시작까지 남은 달로 구간(`bucket`)을 정한다.
4. 공고 연결: `DATA_GO_KR_KEY`가 있으면 청약홈 공고(최근 1095일, 3년)를 모아 `link-notices.js`로 사업에 잇는다. 접수가 오늘 이후까지인 공고가 있으면 `live`.
   공공주택지구는 블록 공고 간격이 1년을 넘기도 해서(하남교산 A2 2025-03) 3년을 본다.
   서울 정비사업 중 현재 단계가 사업시행인가 전(구역지정·추진위·조합설립·건축심의)인 사업에는 공고를 잇지 않는다(`notices` 빈 배열, `live` 아님, `announced` 아님, `linked`에 세지 않음).
   이 단계에서는 자기 분양 공고가 있을 수 없고, 맞는 공고는 같은 지번·구역명의 이웃 단지 공고다(예: 성수1 건축심의에 장미아파트의 `오티에르 포레`).
   규칙은 `canLinkNotices`(`link-notices.js`). 단계를 모르는 사업과 공공주택지구는 그대로 잇는다.
   서울 정비사업에 공고는 이어졌지만 모두 접수가 끝났으면 `windowStatus: announced`로 바꾸고 근거를 `청약홈 공고가 이미 있었습니다(<가장 늦은 공고일>)`로 적는다. 기간은 그대로 둔다. 준공(`done`)은 바꾸지 않는다.
   3년을 보면 같은 지번의 예전 사업 공고도 이어질 수 있어서, 단계가 이주·착공·일반분양이거나 가장 늦은 공고일이 현재 단계 날짜(`stageDates[stage]`)와 같거나 뒤일 때만 `announced`로 바꾼다.
   그 밖(단계 날짜보다 이른 공고, 단계 날짜나 공고일이 없음)은 공고를 `notices`에 남기고 기간·상태·근거는 그대로 둔다.
   공공주택지구는 블록별로 여러 번 공고하므로 지난 블록 공고가 있어도 규칙·보도 기간과 구간을 그대로 두고, 공고는 상세의 분양 이력에 합쳐 보여 준다.

5. 분양 성과: 블록별 분양 지구에서 공고가 난 분양 블록의 분양가, 경쟁률, 주변 시세 비교를 블록별 현황 줄에 붙인다(아래 "분양 성과"). 실패해도 빌드는 계속한다.

서울 자료가 실패하거나 `newtowns.yaml`이 형식에 맞지 않으면 0이 아닌 코드로 끝나 이전 배포가 유지된다.
서울 자료에서 단계나 사업유형 값을 몰라 건너뛴 행(`skipped.stage + skipped.kind`)이 데이터 행의 5%를 넘어도 `seoul_values`로 멈춘다. 원자료의 값 이름이 바뀐 경우다. 건너뛴 수는 `sources.seoul.skipped`와 로그에 남는다.
공고 연결 실패는 `notices.skipped`에 오류 종류만 남기고 계속한다. 키가 없으면 `skipped=no_key`.

로그 예: `map seoul=496 skipped=0 asOf=2026-06 towns=3 notices checked=812 linked=4`(건너뛴 행이 있으면 `skipped=stage:1,duplicate:2`), 이어서 구간별·단계별 건수,
마지막에 분양 성과 건수 `map performance blocks=4 priced=4 estimated=2 competition=3 calls=60 errors=0`(키가 없으면 끝에 `skipped=no_key`).

## 예상 시기 규칙

현재 단계의 날짜부터 센다. 날짜가 없으면 오늘부터 세고 근거에 `날짜 없음, 오늘 기준`이라고 적는다.

| 유형 | 현재 단계 | 예상 분양 시기 |
|---|---|---|
| 재개발·재건축 | 구역지정·추진위·조합설립·건축심의 | 없음, `far` (사업시행인가 전이라 36개월 밖으로 예상) |
| | 사업시행인가 | 3~5년 뒤 |
| | 관리처분인가 | 1.5~3년 뒤 |
| | 이주 (관리처분이고 이주시작일이 자료 기준월 말일까지) | 0.5~2년 뒤 |
| | 착공 | 0~1년 뒤 (일반분양은 착공 전후가 많음) |
| 공공주택지구 | 후보지 | 없음, `far` |
| | 지구지정 | 3~5년 뒤 |
| | 지구계획승인 | 1.5~3년 뒤 |
| | 부지조성 착공 | 1~2년 뒤, 블록별 순차 공고 |
| | 블록별 분양 | 다음 블록 예상. 아래 "블록별 분양 지구" 참고 |
| | 준공 | 없음, `done` |

- `newtowns.yaml`에 `expected`(보도된 계획)가 있으면 규칙보다 우선한다(블록 계획보다도 먼저).

### 블록별 분양 지구

이미 블록 본청약이 시작된 지구의 기간은 첫 청약이 아니라 **다음 블록** 예상이다. 사업에 `windowLabel: '다음 블록 예상'`을 붙이고(다른 사업은 `null`), 사이트는 예상 칸·목록·타임라인에서 '예상 청약' 대신 이 이름으로 보여 준다(`다음 블록 예상 2026-11~2026-12`).
보도된 블록 계획(`plans`)이 먼저이고, 없으면 오늘부터 0~2년이다.

1. `plans` 중 임대가 아닌 계획(`rental: true` 제외)만 본다. `expected`는 `YYYY-상반기` → 1~6월, `YYYY-하반기` → 7~12월, `YYYY-MM` → 그 달.
   아래 중 하나의 날짜가 하한과 같거나 뒤면 그 블록은 공고가 난 것으로 보고 뺀다. 계획 시기보다 이른 공고(앞당겨 공고)도 뺀다.
   - 같은 블록의 본청약 이력(`history`, 임대·사전청약 제외)의 공고일
   - 이 지구에 이어진 청약홈 공고 중 공고명에 그 블록 이름이 있는 것(`nameHasBlock`, 임대 유형·민간사전청약 제외)의 공고일.
     예: 접수 중인 `하남교산 A9블록 공공분양` 공고가 이어지면 A9는 근거에서 빠지고 A11만 남는다.
   이 규칙(`blockAnnounced`, `src/pipeline/expected-window.js`)은 블록별 현황의 계획 판단과 같은 함수다. 그래서 공고 연결 뒤 블록별 분양 지구는 기간을 다시 계산한다.
   하한은 계획 보도일(출처 중 가장 이른 날짜), 출처에 날짜가 없으면 지구의 `stageDates['블록별 분양']`, 그것도 없으면 하한 없음.
   둘 다 일까지 있으면 날짜로, 하나라도 달까지만 있으면 달로 비교한다. 오늘 뒤 날짜의 이력은 보지 않는다. 사전청약은 어떤 경우에도 계획을 채우지 않는다.
   블록 이름은 공백과 끝의 `BL`·`블록`, 글자와 숫자 사이 `-`만 빼고 비교한다(`A-1` = `A1` = `A1BL`, `A2-1` ≠ `A21`).
2. 출처에 날짜가 하나도 없는 계획은 기간에 쓰지 않는다(근거로 적을 보도일이 없음). 공고가 났는지 보는 데만 쓴다.
3. 남은 계획 중 기간 끝이 이번 달 이후인 것이 있으면 가장 이른 기간(같은 기간이면 블록을 합침). 규칙 `town-plan`.
   기간 시작은 이번 달보다 앞서지 않게 자른다(2026-11에 `2026-하반기` 계획이면 `2026-11~2026-12`). 지난 달만 있는 기간은 보여 주지 않는다.
   근거 `보도된 다음 블록 계획: A9·A11 2026-하반기 (하남일보 2026-03-08). 지역지 보도만 있음. 2026-11-10까지 공고 없음`.
   근거에는 날짜 있는 첫 번째 출처를 적는다. 보도한 곳은 출처의 `outlet`, 없으면 제목 끝 괄호, 없으면 주소의 호스트.
   공식 자료(`*.go.kr`, LH·SH·GH, 청약홈 주소) 없이 보도뿐인 계획이면 끝에 계획의 `note`(합친 계획들의 서로 다른 note), 없으면 `공고 미확인`을 붙인다.
4. 남은 계획이 있지만 모두 지났으면 오늘부터 12개월. 규칙 `town-plan-late`,
   근거 `보도된 일정(D2·D5 2026-상반기, A9·A11 2026-하반기)이 지났지만 공고는 아직 없습니다. 남은 블록 순차 공고`(남은 블록과 시기, 기간 순).
5. 남은 분양 계획이 없으면(계획 없음, 임대 계획만, 날짜 없는 계획만, 모두 공고됨) 확장 규칙: 오늘부터 0~2년, 근거 `다음 블록 예상(규칙): 오늘부터 0~2년`.
   접수 중인 청약홈 공고가 이어졌으면(`live`) 구간은 `live`로 두고, 확장 규칙 기간은 그 공고 마감 달 다음 달부터 2년으로 다시 잡는다
   (근거 `다음 블록 예상(규칙): 접수 중인 공고(마감 2026-12-02) 뒤 0~2년`). 블록 계획·지구 계획(`expected`)으로 잡은 기간은 그대로다.

모두 `status: estimated`라 구간은 기간 시작으로 정한다. 지난 블록 공고가 연결돼도 기간은 그대로다(위 공고 연결 참고).
`plans`는 yaml 이력만 보고 연결된 청약홈 공고는 보지 않는다. 계획한 블록의 공고가 나면 `history`에 손으로 적는다.

### 그 밖의 규칙

- 이주시작일이 자료 기준월(예: 6월 기준이면 6월 말일) 뒤면 아직 예정이라 관리처분인가로 둔다.
- 기간 끝이 이번 달보다 앞이면 기간은 그대로 두고 단계로 가른다.
  - 이주·착공·일반분양: `likely_sold`(예상 시기가 지났습니다. 이미 분양했을 가능성이 큽니다(공고 미확인)). 공고 연결이 안 됐을 뿐 이미 분양했을 가능성이 크다.
  - 그 앞 단계(사업시행인가, 관리처분인가, 공공주택지구 단계): `overdue`(예상 시기가 지났습니다(지연 가능성)).
- 구간(정렬 순서): `live`(접수 중인 공고 연결) → `soon`(기간 시작까지 12개월 미만) → `mid`(36개월 미만) → `far`(나머지와 기간 없음) → `announced`(서울 사업에 지난 공고만 연결) → `overdue` → `likely_sold` → `done`.
  `announced`, `overdue`, `likely_sold`, `done`은 상태 그대로 구간이 된다. 사이트도 같은 규칙으로 다시 계산하므로(만든 뒤 달이 바뀌어 기간이 지나면 단계로 가름) 두 `bucketOf`는 같게 고친다. `test/map-site.test.js`의 공용 표 검사가 둘을 비교한다.
- 사이트: `announced`는 "공고 있었음"(초록 테두리), `likely_sold`는 "분양했을 가능성"(흐린 칩). 둘 다 1년/3년 필터와 구 타일의 1년·3년 집계에서 빠진다.

## 공고 연결 규칙

- 서울: 공고 주소에 같은 구가 있고(공고 지역도 서울), 주소에 사업의 동과 본번(`신영동158`, 공백과 `번지` 무시)이 있거나 공고명에 구역명(`구역`과 공백을 뺀 값, 3글자 이상)이 있으면 잇는다. 숫자로 끝나는 값은 뒤에 숫자, `차`, `단지`, `동`, `가`가 이어지면 다른 것으로 본다(`신당1` ≠ `신당10`, `신길2` ≠ `신길2차`·`신길2동`). 지번이 여럿인 주소(`이촌동193-3,5`, `청담동65,삼성동53-2`)는 첫 지번만 쓴다.
  현재 단계가 사업시행인가 전(구역지정·추진위·조합설립·건축심의)이면 맞는 공고가 있어도 잇지 않는다(`canLinkNotices`, 위 파이프라인 4 참고).
- 공공주택지구: 공고 주소나 이름에 시 이름(`하남`)과 `noticeMatch` 중 하나가 있어야 한다.

## 사업별 최근 뉴스 (`src/pipeline/news.js`)

네이버 뉴스 검색 API(공식)로 사업마다 최근 기사 몇 건을 모은다. 스크래핑은 하지 않는다. 아직 `build-map.js`에 연결하지 않은 모듈이다.

- 키: `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`. `NAVER_NEWS_ENDPOINT=hub`(기본, 네이버 API 허브 `naverapihub.apigw.ntruss.com/search/v1/news`, 헤더 `X-NCP-APIGW-API-KEY-ID`/`X-NCP-APIGW-API-KEY`) 또는 `legacy`(developers.naver.com `openapi.naver.com/v1/search/news.json`, 헤더 `X-Naver-Client-Id`/`X-Naver-Client-Secret`). 키는 헤더로만 보내 주소와 오류 문구에 남지 않는다. 키가 없으면 `news_no_key`, 다른 값이면 `news_endpoint`.
- 대상(`newsTargets`): 공공주택지구 전부 + 서울 정비사업 중 `live`·`soon`·`mid`. 서울은 `live` > `soon` > `mid`, 같은 구간은 예상 시기 시작이 이른 순으로 150개까지(`maxSeoul`). 주 1회 실행이면 호출은 160건 안팎으로 하루 한도(25,000건)보다 훨씬 적다.
- 검색어(`newsQuery`): 공공주택지구는 이름(`하남교산`). 서울은 `<구에서 '구'를 뺀 이름> <구역명> <재개발|재건축>`(`종로 신영1구역 재개발`). 구역명이 숫자로 끝나면 `구역`을 붙이고(`신영1` → `신영1구역`), `반포미도2차`·`개포주공5단지`는 그대로 둔다. `중구`는 줄이지 않는다. 최신순(`sort=date`) 20건을 받는다.
- 관련성(`relevant`): 제목(태그·엔티티 제거, 공백 제거)에 이름이 있어야 남긴다. 서울은 공고 연결과 같은 구역명 값(`구역`과 공백을 뺀 값, `신영1구역`·`신영 1구역` 모두 맞음)이고, 3글자 미만이면 `<이름>구역`으로만 찾는다. 공공주택지구는 이름 또는 `noticeMatch`(2글자 이상). 숫자로 끝나는 값 뒤에 숫자, `차`, `단지`, `동`, `가`가 오면 다른 것으로 본다(`신당1` ≠ `신당10`, `신길2` ≠ `신길2차`). 기사 제목에는 구가 거의 없어 구는 보지 않는다(다른 구의 같은 이름 구역이 섞일 수 있다).
- 정리: 같은 링크나 같은 제목(공백·문장부호 무시)은 하나만, 오늘 기준 21일 전(그날 포함)부터 오늘까지만, 최신순 5건(`limitPerProject`)까지.
- 저장하는 값: `{ title, outlet, date, url }`뿐이다. 제목은 `<b>` 태그를 지우고 엔티티(`&quot;`, `&amp;` 등)를 푼 값, 언론사는 원문 주소 호스트로 정한다(알려진 언론사는 이름, 아니면 `www.`를 뗀 호스트). 날짜는 `pubDate`(RFC 1123)의 한국 날짜, 링크는 원문(`originallink`)이 http(s)면 원문, 아니면 네이버 뉴스 링크다. 날짜를 읽지 못한 기사는 보관 기간을 지킬 수 없어 뺀다. 요약(`description`)과 본문은 저장하지 않는다.
- 약관(2026-09 개정 보도 기준): 출처와 원문 링크를 함께 보여 주고, 서버 보관은 21일 이내, AI 학습·답변 생성·재판매에 쓰지 않는다. 사이트에는 언론사 이름과 원문 링크를 함께 보여 줘야 한다.
- 실패: 사업 하나의 실패는 `errors`에 kind만 남기고 다음 사업으로 간다. `401`·`403`·`429`, 키 없음, 잘못된 endpoint는 `stopped`에 kind를 두고 바로 멈춘다(호출을 더 보내지 않음). 사업 사이에 200ms 쉰다.
- 결과(`collectNews`): `{ byId: { [사업 id]: [...] }, checked, matched, errors, failed, stopped }`. 기사가 남은 사업만 `byId`에 있다.
- 연결할 때: `bucketOf` 뒤, `toPublic` 전에 `newsTargets`를 부른다(구간이 필요하고, `toPublic`이 `noticeMatch`를 지운다). 실패해도 지도 빌드는 계속하고 뉴스만 비운다.

## `data/newtowns.yaml` 편집

```yaml
towns:
  - id: hanam-gyosan        # 바꾸지 않는 영문 소문자·숫자·하이픈 (지도 id는 town-<id>)
    name: 하남교산
    region: 경기
    district: 하남           # 시는 빼고 적는다 (출력은 하남시). 구·군이면 그대로 적는다.
    kind: 공공주택지구
    stage: 지구계획승인        # 후보지, 지구지정, 지구계획승인, 부지조성 착공, 블록별 분양, 준공 중 하나
    stageDates:              # 출처로 확인한 날짜만, "YYYY-MM" 또는 "YYYY-MM-DD"
      지구지정: "2019-10"
    households: 33000        # 모르면 비워 둔다
    noticeMatch: [교산]      # 청약홈 공고명·주소에서 이 지구를 가리키는 글자
    expected:                # 선택. 보도된 분양 계획이 있을 때만
      from: "2029-06"
      to: "2031-06"
      basis: "…"
    notes: "…"
    sources:
      - title: "…"
        url: https://...
        date: "2025-12-31"
```

- 날짜는 따옴표로 감싼 문자열로 쓴다.
- 모르는 값은 비워 둔다. 빈 `households`, `stageDates`, `noticeMatch`, `expected`, `notes`, `sources`는 허용한다.
- 단계 이름이 목록에 없으면 `newtowns_stage`, 날짜 형식이 틀리면 `newtowns_date`, id가 겹치면 `newtowns_duplicate`, 필수 값(id, name)이 없거나 형식이 틀리면 `newtowns_field`, YAML 문법 오류는 `newtowns_yaml`로 빌드가 멈춘다. PR 실행에서 바로 드러난다.
- `noticeMatch`는 너무 짧거나 흔한 글자(`토평`처럼 기존 단지 이름에도 쓰이는 것)를 피한다.
- `sources`의 url은 http(s)만 남는다.

### 분양 이력(history)과 다음 블록 계획(plans)

공공주택지구는 블록 공고 이력과 보도된 다음 블록 계획을 적을 수 있다. 이력은 사이트 상세의 "분양 이력"에 나오고, 계획은 다음 블록 예상 기간에만 쓰인다(출력하지 않음).

```yaml
    history:                   # 사전청약·본청약 (선택)
      - block: A2
        stage: 사전청약                # 본청약(비우면 이 값) 또는 사전청약
        type: 공공분양
        households: 1056
        noticeDate: "2021-11-18"
        source: { title: "… (뉴데일리)", url: "https://…", date: "2021-11-17" }
      - block: A2
        type: 공공분양
        households: 1115
        noticeDate: "2025-03-31"
        end: "2025-05-09"              # 선택, 접수 마감(YYYY-MM-DD). 오늘 이후면 블록 상태 '접수 중'
        title: 교산 푸르지오 더 퍼스트   # 선택, 단지 이름(청약홈 공고와 중복을 가리는 데도 쓴다)
        moveIn: "2029-06"              # 선택, 입주 예정(출력하지 않음)
        rental: true                   # 임대 공고면 true
        note: "…"                      # 선택, 엇갈리는 수치 등 조사 메모(출력하지 않음)
        competition:                   # 선택, 보도된 경쟁률(본청약 분양 이력에만). 청약홈 경쟁률 API에 자료가 없을 때만 지도에 쓴다
          scope: 일반공급               # 출처가 말한 범위. 1순위라고 하지 않았으면 1순위라고 적지 않는다
          households: 201
          applicants: 52920
          rate: 263.3                  # 출처 범위(scope)의 경쟁률. 없으면 applicants/households로 계산
          source: { title: "… (뉴시스)", url: "https://…", date: "2025-05-09" }
        source:                        # 하나 또는 목록
          - { title: "… (LH청약플러스)", url: "https://…", date: "2025-03-31" }
          - { title: "… (뉴시스)", url: "https://…", date: "2025-03-31" }
    plans:                     # 보도된 다음 블록 계획 (선택)
      - blocks: [A9, A11]
        type: 공공분양
        households: { A9: 244, A11: 511 }   # 숫자 하나 또는 블록별
        expected: "2026-하반기"              # YYYY-MM, YYYY-상반기, YYYY-하반기
        rental: true                         # 임대 계획이면 true (기간 계산에서 뺌)
        note: "…"                            # 선택, 확인 정도·주의
        source:                              # 날짜 있는 첫 번째 출처가 근거 문구에 나온다(날짜 없는 출처뿐이면 기간에 안 씀)
          - { title: "… (하남일보, 지역지)", outlet: 하남일보, url: "http://…", date: "2026-03-08" }
```

- `noticeDate`(이력)와 `expected`(계획)는 필수다. 날짜는 따옴표로 감싼 `YYYY-MM` 또는 `YYYY-MM-DD`.
- 항목마다 http(s) 주소가 있는 `source`가 하나 이상 있어야 한다. 없으면 `newtowns_source`로 빌드가 멈춘다. `outlet`(보도한 곳)은 선택이다.
- 지역지 보도만 있는 계획은 출처 제목에 `지역지`를 적는다. 원문을 확인하지 못한 일정(검색 요약에만 보이는 값)은 넣지 않는다.
- 날짜·`expected` 형식이 틀리면 `newtowns_date`, 블록 이름이나 필수 값이 없거나 `stage`가 본청약·사전청약이 아니거나 `rental`이 true/false가 아니면 `newtowns_field`.
  예전 키 `preSubscriptions`도 `newtowns_field`로 멈춘다(`history`에 `stage: 사전청약`으로 옮긴다). 그 밖의 모르는 키는 무시한다.
- `competition`은 객체여야 하고 http(s) 출처가 있어야 한다(없으면 `newtowns_source`). 경쟁률이 양수가 아니거나, 경쟁률도 접수·세대도 없거나, 사전청약·임대 이력에 적으면 `newtowns_field`.
  예전 키 `rank1Rate`도 `newtowns_field`로 멈춘다(1순위로 읽혀 `rate`로 바꿨다).
  원문에 있는 수치만 넣는다. 지도에서는 출처 범위(`scope`)와 출처 링크를 함께 보인다.
- `end`(접수 마감)는 출처에 접수 마지막 날(예: 2순위 접수일)이 있을 때만 적는다. 일까지 있는 날짜가 아니면 `newtowns_date`, 공고일보다 앞이면 `newtowns_field`.
  청약홈 공고가 이어지지 않은 이력도 이 값으로 "접수 중"을 보여 준다(블록 상태, 분양 이력의 접수 중 표시). 사업 구간(`live`)은 바꾸지 않는다.
- 사전청약은 본청약 전 예약이라 계획을 채우지 않고(위 1) 사이트의 "최근 분양"에도 세지 않는다.
- 출력(`projects.json`): 공공주택지구마다 `history`(날짜순, 빈 배열 가능)를 `{ block, stage, type, title, households, noticeDate, end, rental, sources }`로 내보낸다(`end`는 없으면 null). `sources`는 http(s)만 남는다.
  `plans`, `moveIn`, `note`는 내보내지 않는다. 서울 사업에는 `history`가 없다.
- 사이트 상세의 "분양 이력"은 `history`와 연결된 청약홈 공고를 합쳐 최근 공고 먼저 보여 준다(날짜·블록·유형·세대·단지 이름·출처, 임대는 "임대", 사전청약은 "사전청약" 표시).
  청약홈 공고는 공고일이 이력과 같고(둘 다 일까지 있으면 같은 날, 아니면 같은 달) 공고명에 블록 이름(`A2`는 `A-2BL`에 맞고 `A20`·`A2-1`에는 안 맞음)이나 단지 이름이 있을 때만 같은 공고로 보고, 그 이력 줄에 청약홈 링크와 접수 중 표시를 붙인다. 애매하면 따로 한 줄로 둔다.
  이력에 없는 청약홈 공고 줄은 유형(`typeLabel`)을 보여 주고, 민간임대·공공지원민간임대는 "임대", 민간사전청약은 "사전청약"으로 표시한다.
  공공주택지구는 "연결된 청약 공고"를 따로 보여 주지 않는다.
- 목록의 공공주택지구에는 "최근 분양 YYYY-MM"(분양 이력과 연결된 공고 중 가장 늦은 공고일)을 붙인다. 임대(이력의 `rental`, 청약홈 민간임대·공공지원민간임대),
  사전청약(민간사전청약 포함), 아파트가 아닌 청약홈 공고(도시형생활주택·오피스텔·생활숙박시설)는 세지 않는다. 구간(칩)은 그대로다.

### 블록별 현황(blocks, blockTotal)

공고 전 블록의 사업승인·착공 같은 블록 단위 사실은 `blocks`에 적는다. 파이프라인(`src/pipeline/blocks.js`)이 `history`, 연결된 청약홈 공고, `plans`와 합쳐 블록마다 상태를 정하고,
사이트는 블록별 분양 단계 지구의 상세에 "블록별 현황"으로 보여 준다. 예상 기간(다음 블록 예상)에는 쓰지 않는다.

```yaml
    blockTotal:                # 선택. 지구 전체 블록 수가 출처에 있을 때만
      total: 39
      approved: 16             # 선택, 그 출처의 사업승인 블록 수(total 이하)
      date: "2025-11-24"       # 선택, 출처 기준일
      source: { title: "… (시티뉴스, 지역지)", outlet: 시티뉴스, url: "http://…", date: "2025-11-24" }
    blocks:                    # 선택
      - block: A5
        type: 나눔형 공공분양      # 선택. 출처에 유형이 없으면 비운다(사이트는 '유형 미확인')
        households: 492           # 선택
        rental: true              # 임대 블록이면 true
        status: 사업승인           # 사업승인, 착공, 계획 보도, 미정 중 하나(비우면 미정)
        statusDate: "2025-11-24"  # 선택, 그 상태를 확인한 날. 승인일 등을 모르면 출처 보도일
        note: "…"                 # 선택, 엇갈리는 수치 등. 사이트 표의 줄에 작게 보인다
        sources:                  # 하나 또는 목록(source도 받는다). http(s) 주소가 하나 이상 있어야 한다
          - { title: "… (시티뉴스, 지역지)", url: "http://…", date: "2025-11-24" }
```

- `block`이 없거나, `status`가 목록에 없거나, `rental`이 true/false가 아니거나, 세대 수가 숫자가 아니면 `newtowns_field`. `statusDate`·`blockTotal.date` 형식이 틀리면 `newtowns_date`.
  출처가 없으면 `newtowns_source`. 같은 블록(`blockKey`가 같고 `rental`도 같음)을 두 번 적으면 `newtowns_duplicate`.
  `blockTotal`의 `total`이 양의 정수가 아니거나 `approved`가 정수가 아니거나 `total`보다 크면 `newtowns_field`.
- 본청약 공고가 난 블록은 `history`에 적고 `blocks`에는 다시 적지 않아도 된다(이력만으로 줄이 생긴다). 이력과 같은 블록을 `blocks`에 두면 `blocks`의 유형·세대 수가 먼저다.
- 모든 숫자·날짜는 출처로 확인한 값만 넣는다. 원문이 일부 깨져 유형을 읽을 수 없으면 `type`을 비운다.

줄 만들기:

- 줄은 `blocks`, `history`, `plans`(임대 계획 포함)에 나온 블록마다 하나다. 이력이나 계획에만 있는 블록도 줄이 된다. 연결된 공고만 있는 블록은 줄을 만들지 않는다(분양 이력에는 보인다).
- 같은 블록이라도 분양과 임대는 다른 줄이다(열쇠 `blockKey` + `rental`). 구리갈매역세권 A-1 신혼희망타운과 A-1 행복주택이 두 줄이 된다.
  블록 이름 비교는 `plans`와 같다(`A-1` = `A1` = `A1BL`).
- 연결된 청약홈 공고는 공고명에 줄의 블록 이름이 있으면 그 줄(`nameHasBlock`, 분양 이력과 같은 규칙)에 먼저 붙인다.
  공고명에 블록 이름이 없을 때만 이력의 단지 이름(4글자 이상)이 공고명에 있는 줄에 붙인다
  (`교산 푸르지오 더 퍼스트 2차 (A-9BL)`은 A2의 단지 이름이 들어 있어도 A9 줄). 블록처럼 보이는 이름(`A-30BL` 등)이 있는데 맞는 줄이 없으면 붙이지 않는다.
  민간임대·공공지원민간임대 공고는 임대 줄, 그 밖은 분양 줄에만 붙는다. 맞는 줄이 없으면 붙이지 않는다.
- 유형·세대 수: `blocks` 값, 없으면 가장 늦은 본청약 이력(없으면 가장 늦은 이력), 없으면 계획(세대 수는 블록별 값, 블록이 하나면 계획 합계).

상태(앞이 먼저, `statusDate`):

1. `접수 중`: 이 줄에 붙은 공고나 이력(`end`, 사전청약 제외)의 접수 마감이 오늘 이후. 날짜는 마감일.
2. `본청약 공고`(분양 줄) / `임대 공고`(임대 줄): 오늘까지의 본청약 이력이나 접수가 끝난 연결 공고(무순위 등 포함, 사전청약 제외). 날짜는 그중 가장 늦은 공고일.
   공고가 났다는 뜻일 뿐 분양이 다 끝났다는 뜻은 아니다(미계약·잔여 공급이 있을 수 있음).
3. `다음 예정(보도)`: 아직 공고가 안 난 계획 중 기간이 이번 달 이후까지인 것. 공고가 났는지는 `plans`의 규칙(위 1, `blockAnnounced`)과 같은 함수로
   지구의 본청약 이력과 이어진 공고 전체를 본다(공고명에 그 블록 이름이 있는 공고). 임대 계획은 임대 이력·임대 공고로 본다.
   날짜는 계획 출처 중 가장 최근 보도일(`plan.source`와 같은 출처, 날짜 없는 출처뿐이면 null).
4. `예정 지남(보도)`: 공고가 안 난 계획이 모두 기간이 지났다(`2026-상반기` 계획이 2026-07 이후에도 공고 없음). 날짜·`plan`은 3과 같다.
   같은 줄에 기간이 남은 계획이 있으면 그 계획으로 3이 된다.
5. `blocks`의 `status`: `착공` > `사업승인` > `계획 보도`. 날짜는 `statusDate`.
6. `미정`.

사전청약은 상태를 바꾸지 않고 경과(`timeline`)에만 보인다. 정렬은 상태 순서 → 블록 이름(숫자는 크기순, `A5` < `A9` < `A11`) → 분양 줄 먼저.

출력(`projects.json`, 공공주택지구마다):

- `blocks`: `[{ block, type, households, rental, status, statusDate, timeline: [{ stage, date }], plan, note, sources }]`.
  `timeline`은 이력(`사전청약`·`본청약`, 날짜는 공고일)과 이력에 없는 연결 공고, 접수 중인 공고·이력은 `{ stage: '접수 중', date: 마감일 }`(같은 마감일은 한 번), 날짜순.
  연결 공고의 단계는 민간사전청약이면 `사전청약`, 무순위·임의공급·불법행위 재공급과 유형 이름에 `잔여`가 있는 공고는 그 유형 이름, 그 밖은 `본청약`.
  `plan`은 `다음 예정(보도)`·`예정 지남(보도)` 근거 계획 `{ expected, from, to, source }`(공고가 났으면 null). `sources`는 `blocks`·이력·청약홈 공고·계획 출처를 주소 중복 없이 모은 것(http(s)만).
- `blockSummary`: 상태별 줄 수(`{ '본청약 공고': 1, '예정 지남(보도)': 2, 사업승인: 15 }`, 상태 순서, 0은 뺌). `예정 지남(보도)`는 `다음 예정(보도)`와 따로 센다.
- `blockTotal`: `{ total, approved, date, outlet, sources }` 또는 null.
- 서울 사업에는 셋 다 없다. yaml의 `blocks`는 내부 값 `blockEntries`로 읽고 출력하지 않는다.

사이트("블록별 현황", 블록별 분양 단계의 공공주택지구 상세, "분양 이력" 위):

- 위에 상태별 칩과 줄 수, 출처가 있으면 출처가 한 말임을 앞에 밝혀 `시티뉴스(2025-11): 39개 블록 중 16개 사업승인`(출처 링크).
  이 수치는 보도 기준이라 표의 `사업승인` 칩 수(출처로 확인해 넣은 줄, 공고가 난 블록은 다른 상태)와 같은 집합이 아니다. 표 아래 안내에도 적는다.
  칩 수는 사이트가 오늘 기준으로 다시 센다. 빌드 뒤 접수 마감이 지난 `접수 중` 줄은 `본청약 공고`(임대 줄은 `임대 공고`)로 바꾸고 날짜는 가장 늦은 공고일로 둔다.
  빌드 뒤 계획 기간(`plan.to`)이 지난 `다음 예정(보도)` 줄은 `예정 지남(보도)`로 바꾼다(칩은 점선 테두리 `c-over`).
- 표: 블록 · 유형(임대 줄은 "임대", 유형이 없으면 "유형 미확인") · 세대 · 상태와 날짜(접수 중은 "마감 날짜") · 경과(사전청약·본청약·무순위 등, 임대 줄의 본청약은 "공고")와 다음 예정(`2026-하반기 (하남일보 2026-03-08)`, 기간이 지났으면 "· 지남"), 메모 · 출처 링크.
- 480px 이하에서는 표 줄을 카드로 쌓는다(칸 이름은 `data-label`). 페이지 가로 스크롤은 없다. 모든 글자는 textContent, 주소는 `safeHttpUrl`을 거친다.
- "분양 이력" 목록은 그대로 둔다(단지 이름·연결 공고 줄 등 표에 없는 정보가 있다).

### 분양 성과(performance)

블록별 분양 지구에서 이미 공고가 난 분양 줄(임대 줄 제외)마다 분양가, 경쟁률, 주변 시세 비교를 붙인다.
코드는 `src/pipeline/block-performance.js`(대상·계산·붙이기)와 `src/pipeline/applyhome-competition.js`(경쟁률 API).

대상(`performanceTargets`): 블록별 현황 줄에 이어진 청약홈 공고(줄 붙이기와 같은 `noticeRowKey` 규칙) 중 APT 본청약 공고(`kind: apt`, 민간사전청약·무순위·임대 제외)의 가장 늦은 것.
공고 키(주택관리번호·공고번호)는 공고 연결 때 받은 청약홈 공고의 것을 그대로 쓴다(손으로 넣지 않음). 연결된 공고가 없어도 그 블록의 본청약 이력에 보도된 경쟁률(`competition`)이 있으면 대상이다.

- 분양가: 청약홈 주택형(`createModelLookup`, 실행에 하나. 첫 시간 초과·네트워크 실패 뒤에는 남은 블록의 주택형을 부르지 않고 `주택형 조회 실패`로 둔다)의 최고 분양가(`LTTOT_TOP_AMOUNT`, 만원)와 만원/전용㎡. 공급면적은 읽지 않아 평당가는 없다.
  대표 주택형은 전용 84㎡ ±3 중 84에 가장 가까운 것(같으면 비싼 것), 없으면 가장 넓은 것.
- 경쟁률: 청약홈 경쟁률 API(data.go.kr 15098905, `getAPTLttotPblancCmpet`)로 주택형별 1순위 접수건수(`SUBSCRPT_RANK_CODE`=1인 행의 `REQ_CNT`를 모든 거주지역에 걸쳐 합)를 공급세대수(`SUPLY_HSHLDCO`, 주택형마다 한 번)로 나눈다.
  단지 1순위 경쟁률은 주택형 합계끼리 나눈다. `CMPET_RATE` 문자열(미달, `-`, `△`, 쉼표)은 믿지 않고, 접수건수를 못 읽고 1순위 행이 하나뿐일 때만 쓴다. 접수건수 < 세대면 `미달`.
  API에 자료가 없으면(접수 전, LH 공고 미제공 등) yaml 이력의 `competition`(보도)을 쓰고 출처를 보인다. API 값이 먼저다.
  분모 검사: 한 주택형의 `SUPLY_HSHLDCO`가 거주지역 행마다 다르거나(지역별 배정 세대일 수 있음), 같은 `HOUSE_TY`가 주택형 정보에 없거나,
  주택형 정보의 세대수(`households`, 일반+특별공급 합계)보다 크면 그 블록의 API 값을 쓰지 않는다(오류 `competition_households_mismatch`, 보도 값으로).
  주택형 정보의 세대수는 특별공급을 포함해 일반공급 세대수와 같을 수 없어서 "넘지 않음"만 본다. 주택형 조회가 실패하면 거주지역 검사만 한다.
  접수건수나 공급세대수를 못 읽어 빠진 주택형이 하나라도 있으면 일부 주택형만 더한 단지 경쟁률을 내지 않는다(오류 `competition_partial`, 보도 값으로).
  값이 없을 때 사유(`competitionReason`)는 경우마다 다르다: 키 없음, 401·403이면 `경쟁률 API를 쓸 수 없습니다`, 그 밖의 조회 실패,
  접수 시작 전·접수 중(`overallEnd` ≥ 오늘)이면 `접수 전이라/접수 중이라 아직 집계 전입니다`, 접수가 끝났는데 행이 없으면
  `청약홈 경쟁률 자료에 이 공고가 없습니다(LH 청약플러스 접수 공고는 빠질 수 있음)`, 행은 있는데 1순위 값을 못 읽으면 그 사유.
  2026-11 실호출에서 LH 공고(하남교산 A2, 구리갈매 A-1·A-4, 2025년)는 API가 오류 없이 빈 결과를 냈다(LH 청약플러스 접수분은 청약홈 경쟁률에 없는 것으로 보임).
  401·403이면 활용신청 승인 전으로 보고 그 실행에서는 더 부르지 않는다(오류 `competition_http_403`). 그 밖의 오류는 `competition_http_<상태>`, `competition_parse`, `competition_page_limit`.
- 주변 시세: 알림 배치와 같은 순수 함수(`cleanTrades`, `buildSubject`, `estimateBestMargin`)로 대표 주택형 하나를 두 번 추정한다.
  공고 당시는 `today = 공고일`(공고 전 완결 6개월 실거래), 현재 기준은 `today = 빌드일`. 국토부 매매·분양권 클라이언트는 실행에 하나라 같은 시군구·달은 한 번만 부른다.
  공고 단지는 지번·역 도보 없이 신축으로 본다(역 보정 없음, 신뢰도 최대 중). 값은 "같은 조건의 신축이면 얼마"인 신축 환산 추정이다.
  할인율은 `1 − 최고 분양가 / 추정 시세`. 안전 마진(옵션·취득세 차감), 보수 시세, 로또 판정은 쓰지 않는다.
  공고 당시 값은 지금 집계한 실거래(늦은 신고·취소 반영)로 계산해 공고 당시 알 수 있던 값과 조금 다를 수 있다(사이트에 `(현재 집계 기준)` 표시).
  분양권 전매(`RTMSDataSvcSilvTrade`) 조회가 한 번이라도 실패하면(시간 초과, 오류, 예산 초과) 그 실행의 남은 블록 모두 분양권 없이 추정하고(실패가 이어짐)
  신뢰도를 한 단계 낮춘다. 역 보정이 없어 신뢰도가 최대 중이라, 이 경우 모든 블록의 시세 숫자가 신뢰도 하로 숨겨질 수 있다.
  원인은 `sources.performance.errors`(예: `presale_timeout`, `presale_budget`)에 남는다.
- 숨김(값 null과 사유): 신뢰도 하, 추정 없음(비교 단지 부족), 실거래 조회 실패, 시군구 미매핑, 주택형 조회 실패.
  제한 유형(이름·유형에 신혼희망·나눔형·토지임대·지분적립, 또는 청약홈 유형 10)은 시세 차익을 그대로 갖지 못해 시세 비교를 하지 않는다(분양가·경쟁률은 보인다).
- 키(`DATA_GO_KR_KEY`)가 없으면 청약홈·국토부를 부르지 않고 보도된 경쟁률만 붙는다(`skipped: no_key`).
- 블록마다 따로 처리한다. 한 블록의 오류는 그 블록의 사유와 `sources.performance.errors`(종류만, 중복 없음)에 남고, 이 단계 전체가 예외를 내도 `performance_failed`로 남기고 지도는 만든다.

출력: 블록 줄의 `performance`(성과가 없는 줄에는 키가 없음).

- 경쟁률: 청약홈은 `1순위 263.3:1 (접수 52,920건 / 201가구) · 청약홈 실시간 집계, 최종 발표와 다를 수 있음`, 보도는 출처가 말한 범위 그대로 `일반공급 263.3:1 (52,920명 / 201가구) · 뉴시스 2025-05-09`(링크).
- 주변 시세 비교: `공고 당시 주변 신축 환산 시세 9억 원 대비 분양가 29% 낮음 (신뢰도 중, 하남시 비교 3개 단지: …, 실거래 41건, 2024-09~2025-02)`, 이어서 `현재 기준 …`.
  공고 당시 숫자 줄 끝에는 `(현재 집계 기준)`을 붙인다(오늘 받은 실거래로 다시 계산한 값). 숨긴 값은 `공고 당시: 사유 (기간)`, 시세 비교를 하지 않은 블록은 사유만.
  숫자를 보인 줄이 하나라도 있을 때만 아래에 `주변 단지 실거래로 추정한 값이며 이 단지의 시세가 아닙니다 (전매제한·미입주)`를 붙인다.
- 모든 글자는 textContent, 주소는 `safeHttpUrl`을 거친다.

## 로컬 실행

```sh
cd scripts/chungyak-alert
npm ci
npm run build-map                     # 서울 자료를 내려받아 site/projects.json 생성
node src/pipeline/build-map.js --out site/projects.json --seoul-file ./seoul.xlsx   # 내려받은 파일로
node src/pipeline/build-map.js --newtowns ./other.yaml                              # 다른 지구 파일로
npx serve site                        # 또는 아무 정적 서버로 site/ 열기
# 주소 뒤에 ?sample=1 을 붙이면 projects.json 대신 site/sample-projects.json(예시 자료, 예시 안내 표시)을 읽는다
```

`DATA_GO_KR_KEY`가 없으면 공고 연결과 분양 성과의 청약홈·국토부 조회를 건너뛴다(보도된 경쟁률만 붙음).
분양 성과의 경쟁률은 data.go.kr 15098905에 따로 활용신청해야 한다(같은 키). 승인 전이면 `competition_http_401/403` 하나만 남기고 보도 값으로 넘어간다.

## 배포

`.github/workflows/chungyak-map.yml`이 매주 화요일 06:00(KST), 수동 실행, `main`에 이 패키지나 워크플로 변경이 합쳐질 때(push) 만들고 `main`에서만 GitHub Pages로 배포한다.
PR에서는 빌드와 아티팩트 업로드까지만 한다.
같은 PR 브랜치의 이전 실행은 새 커밋이 오면 취소되고, 예약·수동·push 실행(main)은 서로 취소하지 않고 차례로 돈다.
