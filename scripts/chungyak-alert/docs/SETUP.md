# 설정 안내

이 저장소는 공개 저장소입니다. 키, 받는 메일, Notion ID는 파일에 쓰지 말고 GitHub Secrets에만 넣으세요.

## 1. 공공데이터포털 (data.go.kr)

1. 회원 가입 후 다음 6개 API를 활용신청합니다.
   - 청약홈 분양정보 조회 서비스 (15098547)
   - 국토교통부 아파트 매매 실거래가 상세 또는 해당 자료 (15126469)
   - 국토교통부 아파트 분양권전매 실거래가 자료 (15126471). 승인 전에도 배치는 돌아갑니다. 오류 메일 없이 시세 신뢰도가 한 단계 낮아지고 로그에 `presale_` 건수만 남습니다.
   - 국토교통부 공동주택 단지 목록제공 서비스 (15057332)
   - 국토교통부 공동주택 기본 정보제공 서비스 (15058453). 이 둘은 승인 전에도 배치가 돌아갑니다. 비교 단지의 역 보정이 빠지고 신뢰도가 낮아지며 오류 메일 없이 로그에 건수만 남습니다.
   - LH 임대공고 조회
2. 마이페이지에서 일반 인증키를 복사해 `DATA_GO_KR_KEY`로 등록합니다. 디코딩 키를 권장합니다. 인코딩 키를 넣어도 코드가 풀어서 씁니다.

## 2. Notion

1. https://www.notion.so/my-integrations 에서 이 배치에 쓸 내부 통합의 토큰을 `CHUNGYAK_NOTION_KEY`로 등록합니다. 저장소의 기존 `NOTION_KEY` Secret은 다른 통합의 것이므로 쓰지 않습니다. 워크플로가 이 값을 환경 변수 `NOTION_KEY`로 넘깁니다.
2. 대상 페이지의 연결 메뉴에서 그 통합을 추가합니다.
3. 페이지 URL 끝의 32자리 ID를 `CHUNGYAK_NOTION_PAGE_ID`로 등록합니다.

첫 실행 때 데이터베이스, 소스 목록 페이지가 자동 생성되고, 첫 주간 메일 뒤 "청약 배치 상태" 페이지가 생깁니다. 이 페이지 제목의 날짜가 주간 메일 중복을 막으니 지우거나 고치지 마세요.

## 3. 카카오

앱 설정은 끝났습니다.

- [x] 카카오 로그인 활성화
- [x] 동의 항목 "카카오톡 메시지 전송"(`talk_message`) 선택 동의
- [x] Redirect URI `http://localhost:8080/callback` 등록
- [x] Web 사이트 도메인 `https://www.applyhome.co.kr` 등록. 카카오 문서상 메시지 링크에 필수입니다.

카카오맵 사용 설정은 필요 없습니다. 이 배치는 카카오 지도와 로컬 API를 쓰지 않으므로 켜 두었다면 꺼도 됩니다. 메시지 발송과 토큰 갱신에는 영향이 없습니다.

남은 작업은 다음과 같습니다.

1. 앱의 REST API 키를 `KAKAO_REST_KEY`로 등록합니다.
2. 클라이언트 시크릿을 켰다면 값을 `KAKAO_CLIENT_SECRET`으로 등록합니다. 쓰지 않으면 비워 둡니다.
3. PC에서 최초 인증을 1회 실행합니다.

   ```powershell
   cd scripts/chungyak-alert
   $env:KAKAO_REST_KEY = "REST 키"
   $env:KAKAO_CLIENT_SECRET = "시크릿, 없으면 이 줄 생략"
   node kakao-auth.js
   ```

4. 출력된 주소를 열어 동의하면 `.kakao-token.txt`가 생깁니다. 내용을 `KAKAO_REFRESH_TOKEN`으로 등록한 뒤 파일을 지웁니다. 이 파일은 커밋되지 않도록 제외되어 있습니다. 동의 화면에서 메시지 전송 항목을 꼭 선택하세요. 선택 동의라 해제하면 발송이 실패합니다.

## 5. Secret 쓰기용 PAT

카카오 갱신 토큰이 교체되면 워크플로가 Secret을 직접 갱신합니다.

1. GitHub Settings > Developer settings > Fine-grained personal access tokens에서 새 토큰을 만듭니다.
2. Repository access는 **이 저장소만** 선택합니다.
3. Repository permissions에서 **Secrets: Read and write**만 줍니다.
4. 값을 `KAKAO_SECRET_WRITER_PAT`으로 등록합니다.
5. **토큰은 만료됩니다.** 만료일을 정하고 그 전에 갱신하도록 달력에 적어 두세요. 만료되어도 평소에는 문제가 드러나지 않다가 갱신 토큰이 교체되는 날 실패합니다.

## 7. 확인 순서

Actions 탭에서 `chungyak-alert`를 수동 실행합니다.

1. `dry-run`: 수집과 판별만 합니다. Notion은 관심 후보를 세려고 읽기만 합니다. 로그에서 건수와 오류 유형을 봅니다. 신청자 정보(`CHUNGYAK_PROFILE`)를 처음 넣거나 바꿨다면 일반 실행 전에 반드시 dry-run을 먼저 돌려 `unapplicable_archive_candidates`(휴지통으로 옮겨질 행 수)와 `collected` 줄의 `unapplicable_*` 건수를 확인하세요. 한 번에 많이 옮기는 것을 막는 장치는 따로 없습니다. PC에서 `--print`로 실행하면 빼는 공고에 `(unapplicable:region)`, `(unapplicable:ended)` 표시가 붙어 목록을 볼 수 있습니다.
2. `test-send`: 표시된 샘플 메일 1통과 카카오 1건을 보냅니다. Notion에는 쓰지 않습니다.
3. `normal`: Notion 저장을 확인합니다. 두 번 실행해 중복 행이 없는지 봅니다.
4. `force-weekly`: 주간 메일을 강제 발송합니다.

### 접수가 끝난 페이지 정리

저장된 접수 종료일이 오늘(KST) 이전인 페이지는 두 경로로 Notion 휴지통으로 옮겨집니다. 영구 삭제가 아니라 휴지통 이동이며, 접수 종료일이 오늘 이후이거나 비어 있는 페이지는 그대로 둡니다.

**주간 메일 발송 때 자동 정리**

- 주간 메일 발송과 발송 기록이 모두 성공한 실행에서만, 긴급 알림까지 끝낸 뒤 정리합니다. `force-weekly`도 포함합니다.
- 메일이 실패하거나 미뤄진 실행, 그 주의 다른 실행, `dry-run`, `test-send`에서는 정리하지 않습니다.
- 일부가 실패하면 오류 메일에 `cleanup_failed`로 표시되고 잡이 실패합니다. 이미 보낸 메일은 그대로이며, 남은 페이지는 다음 주 발송 때 다시 정리됩니다.
- 로그의 `archived`가 옮긴 건수입니다.
- 휴지통으로 옮긴 공고가 정정되어 접수가 다시 열리면 다음 실행에서 새 페이지로 저장됩니다.

**수동 정리 `cleanup-ended`**

수동 실행 전용입니다. 예약 실행에서는 돌지 않습니다.

- 수집, 저장, 메일, 카카오 발송을 하지 않고 카카오 토큰도 갱신하지 않습니다.
- 로그에는 `archived`, `kept`, `failed` 건수만 남고, 하나라도 실패하면 잡이 실패합니다. 메일로는 알리지 않으니 Actions 결과를 확인하세요.
- 잘못 옮겼다면 Notion 휴지통에서 복원할 수 있습니다. 휴지통 보관 기간은 Notion 정책을 따르므로 필요하면 바로 확인하세요.
- PC에서 대상 건수만 보려면 `NOTION_KEY`와 `CHUNGYAK_NOTION_PAGE_ID`를 설정하고 `node src/main.js --cleanup-ended --dry-run`을 실행합니다.

PC에서 조회만 하려면 다음과 같이 실행합니다. `--print`는 쓰기와 발송을 하지 않으며 Actions에서는 무시됩니다.

```powershell
$env:DATA_GO_KR_KEY = "키"
npm run dry-run
node src/main.js --print
```

## 8. 운영 주의

- **60일 규칙:** 공개 저장소의 예약 워크플로는 저장소 활동이 60일 없으면 자동으로 꺼집니다. 꺼지면 Actions 탭에서 `chungyak-alert`를 선택해 **Enable workflow**를 누르세요. 기존 일일 리포트 커밋을 멈추면 이 일이 생길 수 있습니다.
- **카카오 토큰 복구:** `kakao_secret_write_failed` 메일을 받으면 새 갱신 토큰이 저장되지 않은 상태입니다. PAT를 고친 뒤 3장의 최초 인증을 다시 하고 Secret을 등록하세요.
- **갱신 토큰:** 워크플로가 매일 갱신을 실행하므로 알림이 없어도 쓰지 않아 만료되는 일은 없습니다. 카카오 쪽 동의 철회나 비밀번호 변경 등으로 끊기면 `kakao_access_token_missing` 메일이 옵니다.
- **Notion 오류:** Notion을 읽지 못해도 긴급 알림은 보냅니다. 발송 기록을 남기지 못하므로 같은 날 다음 실행에서 또 올 수 있고, 오류 메일에 `urgent_sent_without_stamp`로 표시됩니다. 주간 메일은 발송 기록이 필요해 Notion이 복구된 뒤 보냅니다. 잡은 실패로 끝납니다. 실행 중 Notion이 응답하지 않으면(`notion_timeout`, `notion_network`) 그 실행에서는 Notion 호출을 멈추고 같은 방식으로 처리합니다. 이때 저장하지 못한 공고는 접수가 끝나기 전이면 다음 실행에서 저장됩니다.
- **저장 범위:** 접수가 이미 끝난 공고는 Notion에 새로 넣지 않습니다. 날짜가 없는 LH 공고는 상태에 `마감`이나 `종료`가 들어 있으면 같이 건너뜁니다. 날짜도 마감 상태도 없는 공고는 저장합니다. 이미 Notion에 있는 페이지는 접수가 끝나면 주간 메일 발송 때 휴지통으로 옮겨집니다. 로그의 `skipped`는 이렇게 건너뛴 공고와 접수가 끝나 갱신하지 않은 기존 페이지를 합친 수입니다. 신청자 정보가 있으면 신청할 수 없는 공고도 저장하지 않고 저장된 행을 휴지통으로 옮깁니다(11장 `신청할 수 없는 공고 제외`, 로그 `unapplicable_*`).
- **긴급 알림 유실:** 카카오와 메일이 모두 실패하면 오류 메일 항목 `urgent_lost`가 생기고 잡이 실패합니다. 메일까지 막혀 있으면 이 표시도 받지 못할 수 있으니 Actions 실패 알림을 켜 두세요.
- **청약홈 전체 실패:** 청약홈의 모든 조회가 실패하면 LH가 정상이어도 잡이 실패합니다.
- **관심 알림:** `관심`을 체크한 공고는 `추천 접수일`이 있으면 그날, 없으면 접수 시작일이 오늘(KST)이면 지역과 로또 여부와 상관없이 `[관심 청약]` 카카오톡이 갑니다. 추천 접수일로 보낼 때는 `[관심 청약] … 특별(신혼부부) 오늘 접수`처럼 전형의 짧은 이름을 적습니다. 추천은 이번 실행에서 다시 계산한 값을 쓰므로 공고 날짜가 바뀌어도 따라갑니다. 같은 날 로또 알림과 겹치면 로또 알림 한 건만 갑니다. 마지막 실행(10:00, 지연될 수 있음) 뒤에 체크하거나 접수 시작일이 지난 공고를 체크하면 그 알림은 가지 않습니다. 접수가 끝난 공고는 체크해도 정리 대상입니다.

## 9. 로또 판별 설정

`config.json`의 `lotto.includePriceCap`(분양가상한제), `lotto.includePublicDistrict`(공공주택지구)는 기본값이 켜짐입니다. 수도권의 해당 아파트 공고는 로또 후보가 됩니다. 끄려면 값을 `false`로 바꾸세요.

**조건형 로또의 가격 확인 (2026-11-10):** 조건(무순위·잔여세대, 불법행위 재공급, 임의공급, 분양가상한제, 공공주택지구)은 이제 로또 후보일 뿐이고 최종 판정은 시세로 합니다.

- 가격 기준을 넘거나, 신뢰도 `중` 이상 추정의 안전 마진이 0 이상이면 `로또`입니다.
- 신뢰도 `중` 이상 추정의 안전 마진이 음수면 `아님`이고 판별 근거에 `… 해당이나 시세 대비 이점 없음`이라고 적습니다.
- 추정이 없거나 신뢰도 `하`이면 놓치지 않게 예전처럼 `로또`입니다.
- 주택형이 여럿이면 신뢰도 `중` 이상이면서 가격 기준을 넘는 주택형, 없으면 신뢰도 `중` 이상 주택형 중 마진이 가장 큰 것을 봅니다. 신뢰도 `하`인 주택형의 마진이 더 커도 `중` 주택형을 가리지 않습니다. 그래서 `하` 주택형이 가격 기준을 넘어도 `중` 주택형의 마진이 음수면 `아님`입니다. 이 가운데 단계는 가격을 확인하는 조건형 공고에만 쓰고, 조건 없는 공고는 예전 순서입니다.
- **예외:** 불법행위 재공급은 해지 세대를 예전 분양가로 다시 공급해 대개 실제 로또라 시세와 무관하게 `로또`입니다.
- **무순위 반복 공급:** 공고명에서 무순위·사후·잔여 뒤의 차수(`무순위(사후)(14차)`)를 먼저 보고, 없으면 이름 끝 괄호의 차수(`단지명(14차)`)를 읽습니다. `lotto.remainderMaxRound`(3) 이상이면 추정이 없거나 `하`여도 `아님`입니다(`… 14차 반복 공급`). 다만 신뢰도 `하`라도 가격 기준을 넘으면 놓치지 않게 `로또`입니다. 양의 정수만 쓰고, 끄려면 `null`로 둡니다.
  - 청약홈 API에는 차수 필드가 없습니다. 무순위 공고명은 차수를 이름 끝 괄호에 둡니다. 확인한 사례는 둘입니다: 청약홈 공고문 파일명 `단지명(14차) 무순위 입주자모집공고문`과, 2차 단지가 없는 단일 단지의 무순위 공고명 `…(2차)`. API 응답으로는 확인하지 않았습니다.
  - 단지 차수를 `단지(3차)`처럼 괄호로 적은 이름은 무순위 차수로 잘못 읽습니다. 단지 차수는 보통 괄호 없이(`단지 3차`) 적어 읽지 않습니다. 차수를 모르면 위 규칙대로입니다.
- 조건별 가격 확인은 `lotto.triggerPriceCheck`(`remainder`, `resupply`, `arbitrary`, `priceCap`, `publicDistrict`)로 켜고 끕니다. 기본값은 `resupply`만 `false`입니다. `true`가 아닌 조건은 예전처럼 시세와 무관하게 `로또`이고 반복 공급 규칙도 보지 않습니다. `triggerPriceCheck`가 객체가 아니면(예: `true`, 배열, `null`) 없는 것으로 보고 모든 조건이 예전 동작입니다. `remainderMaxRound`가 `null`도 양의 정수도 아니면(예: `0`, `2.5`, `"3"`) 반복 공급 규칙을 끕니다. 두 경우 모두 로그 `market` 줄에 `soft=bad_trigger_config:1`이 남습니다.
- 이전에 로또였던 공고가 신뢰도 `중` 이상 추정이나 반복 공급으로 `아님`이 되면 이전 판별을 유지하지 않고 `lotto_demoted`로 셉니다.
- **보수적인 마진:** 안전 마진은 보수 시세(검증 오차 최대 10% 차감)에서 분양가, 옵션비, 취득세를 뺀 값입니다. 그래서 시세보다 조금만 싼 조건형 공고도 음수가 되어 `아님`이 될 수 있습니다. 놓칠 수 있다는 것을 알고 고른 규칙입니다.
- **판정이 바뀔 수 있음:** 실거래가 쌓이거나 빠져 추정 신뢰도가 `하`와 `중` 사이를 오가면, 같은 공고가 날마다 `아님`과 `로또` 사이를 오갈 수 있습니다.

`lotto.minMarginManwon`(3억 원)과 `lotto.minMarginRate`(20%)는 안전 마진과 마진율에 적용합니다. 둘 중 하나를 넘으면 가격 기준을 넘습니다. 기준값은 예전 `예상 차익`, `차익률` 기준과 같습니다. 마진율은 2026-11-08부터 보수 시세가 아니라 분양가 대비라서, 같은 20%라도 예전보다 넘기 쉽습니다. 로그의 `lotto_demoted`는 로또에서 빠진 공고만 세고, 이 변경으로 새로 로또가 된 공고는 보여 주지 않습니다. 조건형 로또는 위의 가격 확인을 따르고 판별 근거에 마진을 함께 적습니다. 가격 기준만으로 로또가 되려면 추정 신뢰도가 `중` 이상이어야 합니다. 주택형도 신뢰도 `중` 이상이면서 기준을 넘는 것 중 마진이 가장 큰 것을 고릅니다. 신뢰도 `하`인 주택형의 마진이 더 커도 기준을 넘는 다른 주택형을 가리지 않습니다. `하`이면 기준을 넘어도 `아님`이고 판별 근거 앞에 `가격 기준은 넘지만 추정 신뢰도가 하라 로또로 보지 않음`이라고 적습니다. 반대로 이미 로또로 기록된 공고가 신뢰도 `하`인 추정으로 `아님`이 되려 하면 로또를 유지하고 `이전 판별 유지(이번 추정 신뢰도 하)`라고 적습니다(무순위 반복 공급으로 `아님`이 된 공고는 제외). 약한 추정 하나로 알림이 생기거나 사라지지 않게 하려는 것입니다. dry-run도 읽어 둔 Notion 행으로 같은 규칙을 적용합니다. 토지임대부, 지분적립형, 신혼희망타운은 `market.restrictedNameKeywords`와 신혼희망타운 유형 코드로 찾아 어떤 조건보다 먼저 `대상 외`로 두고 저장된 추정 시세, 안전 마진, 마진율, 시세 신뢰도를 지웁니다. 유형 코드도 함께 봅니다.

## 10. 안전 마진과 시세 보정

**`config.json`의 `market` 값은 모두 판단이 들어간 시작값입니다.** 실측으로 정한 값이 아니므로 정확도를 보장하지 않습니다. 결과를 보고 조정하세요. JSON에는 주석을 쓸 수 없어 여기에 적습니다.

**직접 입력할 값:** Notion의 `역 도보(분)`에 공고 단지에서 가장 가까운 지하철역까지의 도보 시간을 숫자로 넣습니다. 아직 없는 아파트라 공공 데이터에 값이 없어 카카오맵 등을 보고 직접 넣습니다. 배치는 읽기만 하고 덮어쓰지 않습니다. 없으면 역 보정 없이 계산하고 신뢰도는 `중`까지만 오릅니다. 입력이 있는 공고만 공동주택 API를 호출합니다.

계산 순서는 다음과 같습니다. 코드는 `src/market-estimate.js`입니다.

1. 취소, 직거래, 1~2층(`tradeFilter.lowFloorMax`), 토지임대부 거래를 뺍니다. 값이 없는 항목은 거르는 근거로 쓰지 않습니다.
2. 공고 단지의 거래(분양권 포함)가 `sameComplex.minSamples`건 이상이면 보정 없이 그 값을 씁니다. 신뢰도는 `상` 또는 `중`입니다. 이름은 같거나 한쪽이 다른 쪽을 포함하면 같은 단지로 보되, 브랜드를 뺀 부분이 `minDistinctiveLength`자 미만이면 포함 관계를 인정하지 않습니다. 공고 주소에 법정동이 없으면(신도시 블록 주소 등) 이름이 정확히 같을 때만 인정합니다. 포함 관계는 거래 행의 지역이 공고 단지와 같은 읍·면, 리, 동을 가리키거나 비어 있을 때만 인정합니다. 예를 들어 리 없이 `오남읍`만 있는 공고는 지역이 `마석우리`뿐인 행과 이름이 정확히 같을 때만 같은 단지로 봅니다. 읍·면 주소의 리는 읍·면 바로 뒤에 올 때만 읽고, 도로명 뒤의 건물명은 리로 보지 않습니다.
3. 아니면 거래를 단지 단위로 묶습니다. 단지 안의 이상치(`outlierBand`)를 빼고 최근 거래에 가중치(`recencyHalfLifeMonths`)를 둔 단가 하나를 남깁니다.
4. 비교 단지는 연식이 공고 단지와 가까운 단지를 먼저 고릅니다. 지역 범위는 동 주소면 같은 법정동, 시군구 순이고, 읍·면 주소면 같은 리, 같은 읍·면, 시군구 순입니다. 읍·면 공고 단지를 시군구 전체 단지로 재면 다른 생활권(예: 남양주 화도읍과 다산 신도시)일 수 있어 신뢰도를 `하`로 두고 판별 근거에 적습니다. 국토부 자료의 법정동 이름은 `화도읍 마석우리`와 `마석우리` 두 형식을 모두 받지만, 읍·면 이름이 없는 행은 같은 리일 때만 같은 지역으로 봅니다. 그래서 리만 오는 형식이면 같은 읍·면 범위는 비어 있고 시군구로 넓어지며, 판별 근거는 `같은 읍·면 단지를 찾지 못해`라고 적습니다. `market` 줄의 `umd_town`, `umd_village`, `umd_dong`, `umd_other`는 실거래 행의 법정동 이름 형식별 건수라 첫 실행에서 실제 형식을 확인할 수 있습니다. 공고 단지는 입주 전이라 0년으로 보고, `comparables.preferMaxAgeYears`(15년) 이내 단지를 같은 법정동, 같은 시군구 순으로 찾습니다. 표본이 `lotto.minSamples`, 단지 수가 `comparables.minComplexes`(2곳)에 못 미치면 `ageWidenSteps`(25년, 그다음 연식 무관)로 넓힙니다. 25년으로 넓히면 신뢰도를 한 단계 내립니다. 연식 무관으로 고르면 신뢰도는 `중`까지만 오르고, 비교 단지가 `safeValue.minComplexesForLoo`(4곳) 미만이거나 퍼짐과 서로 맞혀 본 오차가 `중` 기준을 넘으면 `하`입니다. 신축 공고 단지를 구축으로 재면 시세가 낮게 잡히므로, 그래도 가격 기준을 넘는 마진은 오히려 작게 잡힌 쪽이라 `중`을 허용합니다. 같은 법정동에 거래가 `lotto.minSamples` 이상 있었는데 연식 때문에 시군구 단지를 고르면 위치가 다른 만큼 한 단계 더 내립니다. 단계 안에서는 표본이 많은 순으로 `maxComparables`곳까지 고릅니다. 같은 법정동에 싸고 거래가 많은 구축이 섞여 있어도 신축 비교 단지가 밀려나지 않게 하려는 것입니다. 좌표가 없어 거리는 보지 않습니다. 시군구 경계 너머의 단지는 보지 않습니다.
5. 단지 단가를 공고 단지 조건으로 환산합니다. 비율은 `공고 단지 계수 / 비교 단지 계수`이고 전체 비율은 `minFactor`~`maxFactor`로 제한합니다.
   - **역 도보(`adjustment.station`):** 5분 이내 1.06, 10분 1.04, 15분 1.02, 20분 1.00, 그 밖 0.97. 공고 단지는 직접 입력한 분, 비교 단지는 공동주택 상세 정보의 지하철역 거리를 씁니다. 값이 구간이면 윗값으로 봐서 `5~10분이내`는 10분, `20분초과`는 그 밖입니다. 구간 표는 시작값이며 실제 시세 차이를 측정한 값이 아닙니다.
   - **브랜드(`adjustment.brand`):** 상위 1.05, 중위 1.02, 그 밖 1.00. 공고 단지는 단지명 키워드, 없으면 청약홈 시공사(`CNSTRCT_ENTRPS_NM`)의 첫 회사로 봅니다. 비교 단지는 실거래 자료에 시공사가 없어 단지명으로만 봅니다. 그래서 브랜드가 이름에 없는 비교 단지는 시공사가 대형사여도 중립으로 계산되어, 같은 조건의 공고 단지보다 낮게 평가될 수 있습니다. 모르는 브랜드는 중립입니다.
   - **연식(`adjustment.age`):** 1년에 0.5%, 최대 20년(0.90). 10년 된 역세권 상위 브랜드 단지가 입주 전 무브랜드 단지보다 낮아지지 않게 잡은 값입니다. 공고 단지는 입주 전이라 신축으로 봅니다. 건축년도를 모르는 비교 단지는 보정하지 않고, 분양권 거래만 있는 단지는 신축으로 봅니다.
6. **비교 단지 역 값 찾기:** 실거래 단지명을 공동주택 목록의 단지명과 맞춥니다. 같은 법정동에서는 이름이 같거나 2번과 같은 규칙으로 포함될 때, 시군구 전체에서는 이름이 정확히 같을 때만 받습니다. 브랜드만 있는 이름은 받지 않고 후보가 여럿이면 고르지 않습니다. 못 찾은 단지는 역 계수를 받지 않습니다. 값이 있는 단지 비율이 `comparables.minStationShare`(0.6)보다 낮으면 섞지 않고 그 주택형 전체에서 역 보정을 뺍니다.
7. 보정 뒤 단지별 단가의 중위값(짝수 개면 가운데 둘의 평균)에서 `outlierLow`(0.7배) 아래나 `outlierHigh`(1.4배) 위인 단지를 뺍니다. 벗어난 단지가 고른 단지의 `outlierMaxShare`(25%)를 넘으면 시세가 둘로 갈린 것으로 보고 빼지 않으며, 빼고도 `outlierMinRemaining`(4곳) 이상 남을 때만 뺍니다. 신뢰도와 할인율은 빼기 전 전체 단지로 계산합니다. 단지가 짝수 개일 때 추정 시세는 가운데 둘 중 낮은 값이라, 시세가 둘로 갈리면 싼 쪽에 가깝게 잡힙니다. 보수적인 방향이라 그대로 둡니다. `추정 시세`는 남은 단지의 중위값입니다. 단지마다 같은 가중치입니다.
8. `안전 마진`은 `보수 시세 - 최고 분양가 - 옵션비(optionCostManwon) - 취득세`입니다. 보수 시세는 `추정 시세 × (1 - 할인율)`입니다. 할인율은 측정한 오차만 씁니다(2026-11-08 사용자 결정). 비교 단지가 `safeValue.minComplexesForLoo`(4곳) 이상이면 단지끼리 서로를 맞혀 본 오차(leave-one-out)의 중위값과 퍼짐(사분위 범위/중위값)의 절반 중 큰 값을 0~`maxDiscount`(10%)로 씁니다. 오차의 중위값은 다수가 서로 같으면 소수의 큰 차이를 보지 못해 퍼짐으로 보완합니다. 하한은 없고, 이상치를 뺐을 때도 하한을 두지 않으며 신뢰도로 알립니다. 단지가 2~3곳이라 오차를 잴 수 없으면 할인하지 않고 판별 근거에 `비교 단지가 적어 오차를 재지 못해 차감 없음`이라고 적습니다. 이때 신뢰도는 낮추지 않고 10번의 기준(표본 수, 단지 수, 퍼짐)을 그대로 따릅니다. 그래서 2~3곳이 서로 비슷한 값이면 `중`이 되어 가격 기준으로 로또가 될 수 있고, 보수 시세가 추정 시세와 같아 오차만큼의 여유는 없습니다. 판별 근거의 `차감 없음`을 보고 공고문과 시세를 직접 확인하세요. 측정값이 10%를 넘으면 10%만 빼고 판별 근거에 `실제 위험은 더 큼`이라고 적으며 신뢰도는 `하`입니다. 신뢰도 `하`는 가격 기준만으로 로또가 되지 못하므로, 상한에 걸린 추정으로는 로또가 생기지 않습니다. 예전의 하위 25%는 단지 8곳이면 두 번째로 싼 단지 값이라 싼 단지 한두 곳에 끌려갔습니다. 이 방식은 공고 단지를 맞힐 때 예상되는 오차만큼 낮춰 잡습니다. 같은 단지 거래로 계산할 때는 그 거래들의 하위 25%를 그대로 씁니다. `마진율`은 안전 마진을 분양가로 나눈 비율이고, 판별 근거에는 `마진율 -43%(분양가 대비)`처럼 적습니다. 분양가는 평균 분양가가 아니라 마진 계산에 쓴 그 주택형의 최고 분양가입니다. 2026-11-08까지는 보수 시세로 나눠, 시세가 낮을수록 음수가 크게 부풀었습니다(예: 의정부 59.98㎡ -70%, 분양가 대비로는 -43%였고 할인 규칙이 바뀐 뒤로는 단지 1곳이라 차감 없이 -27%). 분양가가 없으면 마진율은 비우고 3억 원 기준만 봅니다. 주택형은 신뢰도 `중` 이상이면서 기준을 넘는 것 중 마진이 가장 큰 것, 없으면 전체에서 마진이 가장 큰 것을 고르고 판별 근거에 적습니다. 가격을 확인하는 조건형 공고만 그 사이에 신뢰도 `중` 이상 주택형 중 마진이 가장 큰 것을 먼저 봅니다(9절).
같은 단지 거래로 계산할 때 분양권 조회가 실패해도, 매매 거래만으로 `sameComplex.minSamples`건을 채우면 신뢰도를 `중` 아래로 내리지 않습니다.

9. **취득세(`acquisitionTax`)는 1주택 유상취득, 감면 없음을 가정합니다.** 6억 원 이하 1%, 9억 원 이상 3%, 그 사이는 직선으로 오르고 지방교육세로 세액의 10%를 더합니다. 분양가 기준이며 전용 85㎡ 초과의 농어촌특별세(0.2%)와 다주택 중과는 넣지 않았습니다. 실제 세액은 다를 수 있습니다.
10. `시세 신뢰도`는 표본 수, 단지 수, 보정값의 퍼짐, 단지끼리 서로를 맞혀 본 오차(`confidence`)로 정합니다. 연식 범위를 넓혔으면 내리거나 `하`로 둡니다(4번). `역 도보(분)`이 비어 있으면 `중`까지만 오릅니다. 입력은 있지만 비교 단지 값이 부족하면 한 단계 내립니다. 분양권 조회가 실패하면 한 단계 내립니다.

**판별 근거:** `역 도보 7분(입력)`처럼 입력 값을, 쓴 비교 단지를 모두 단지명과 공고 주택형 면적 기준 보정 금액(예: `보정 후 84.6㎡ 기준: 광교중흥에스클래스 18.7억`), 역 거리 구간, 브랜드와 연식 보정으로 적고, 고른 범위(법정동 또는 시군구, 연식 범위)와 뺀 이상치 수, 보수 시세의 차감률을 적습니다. 단지명과 금액은 국토부 공개 자료입니다. Notion은 2000자에서 자릅니다. 카카오톡은 200자라 비교 단지 목록 없이 안전 마진, 마진율, 주택형, 신뢰도만 담은 짧은 근거를 보냅니다. 카카오톡이 실패해 메일로 대신 보낼 때는 전체 판별 근거를 함께 붙입니다. 단지명은 `S클래스`와 `에스클래스`처럼 영문과 한글 브랜드 표기를 같게 보고 묶습니다.

**호출 수와 시간:** `역 도보(분)`이 입력되고 같은 단지 거래로 값이 정해지지 않는 공고만 호출합니다. 시군구마다 목록 1회 이상(1,000건에 1회), 공고당 상세 정보 최대 `maxComparables × 주택형 수`회(면적이 겹치면 더 적습니다)이고, 같은 실행에서 같은 조회는 반복하지 않습니다. 실행당 `aptInfo.maxCallsPerRun`(300회)과 `budgetMs`(2분)에서 멈춥니다. 호출은 한 번에 10초까지 기다리고 시간 초과, 네트워크 오류, 5xx, 429는 한 번 다시 시도합니다. 미승인, 응답 형식 차이, 상한 도달을 포함한 모든 실패는 오류 메일 없이 `soft=`에 남고 그 실행의 호출을 멈춥니다. 데이터 없음(결과 코드 03, 항목 없음, 빈 목록)은 실패가 아니라 그 단지나 시군구의 값이 없는 것으로 보고 계속합니다. 판별 근거는 `역 정보 조회를 못 해`와 `비교 단지 역 정보 부족으로`를 구분합니다. 분양권 조회는 `presale.budgetMs`(2분)에서 멈춥니다.

  1. 유형에 `lh.excludeKeywords`(`선택형`, `분양전환`, `일반매각`, `주택매각`, `용지`)가 있으면 뺍니다. 이름에 있어도 빼지만, `lh.nameExcludeUnless`에 적힌 단어가 이름에 함께 있으면 빼지 않습니다. 기본값은 `선택형` → `나눔형`, `일반형`이라 `뉴:홈 공공분양주택 입주자모집공고(나눔형·선택형)` 같은 통합 공고는 남고, `공공분양주택 입주자모집공고(선택형)`처럼 선택형만 적힌 공고는 빠집니다. 선택형 단독 공고도 이름에 `공공분양`이 들어가기 쉬워 `공공분양`은 예외 단어로 쓰지 않습니다.
  2. 유형이 비어 있으면 남깁니다(지역 규칙은 적용).
  3. 유형에서 `lh.forceSaleKeywords`(`토지임대부`)를 지운 나머지에 `lh.nonSaleTypes`(`임대`, `행복주택`, `전세`, `주거복지`, `토지`, `상가`, `매각`)가 있으면 뺍니다(`임대주택 토지임대부`는 빠짐).
  4. 유형에 토지임대부가 있었거나 `lh.saleTypes`(`분양주택`, `공공분양`, `신혼희망타운`, `뉴홈`, `나눔형`, `일반형`)가 있으면 남깁니다. 토지임대부는 제한 유형이라 `로또 여부`는 `대상 외`입니다. 이름의 토지임대부는 유형 판정을 바꾸지 않습니다.
  5. 어느 목록에도 없는 유형은 실제 값을 몰라 남기고(지역 규칙은 적용) `lh_type_unknown`으로 셉니다.
  - 남는 공고: 공공분양(뉴홈 일반형·나눔형 포함), 토지임대부 분양, 신혼희망타운 분양형, LH 분양 잔여·무순위·추가모집. 빠지는 공고: 선택형, 분양전환 공공임대, 토지·용지·상가·매각, 임대.
  - 토지임대부 예외는 두 곳에 더 있습니다. 임대 제외는 유형과 이름에서 `rentalExceptKeywords`를 지우고 봅니다. 수집 단계의 토지·상가 제외(`lh.excludeTypeKeywords`)는 `lh.filterSaleArea`가 켜져 있을 때만 유형에서 토지임대부를 지우고 봅니다(이름은 보지 않음). 꺼 두면 예전처럼 토지임대부 유형도 수집 단계에서 빠집니다.
- **대상 지역:** 공급지역이 `lh.targetRegions`(`서울`)이거나, 공고 이름(공백 제거)에 `lh.targetAreas`의 단어가 있으면 남깁니다. 공급지역(`CNP_CD_NM`)이 비었으면 판정할 수 없어 남기고 `lh_region_unknown`으로 셉니다. 그 밖의 시도와 아래 지구 밖 경기 공고는 뺍니다.
  ```json
  "targetAreas": [
    { "name": "하남교산", "keywords": ["하남교산", "교산"] },
    { "name": "광명시흥", "keywords": ["광명시흥"] },
    { "name": "구리갈매", "keywords": ["구리갈매", "갈매역세권"] },
    { "name": "구리토평", "keywords": ["구리토평", "토평"] },
    { "name": "남양주왕숙", "keywords": ["남양주왕숙", "왕숙"] }
  ]
  ```
  지구를 더하려면 `config.json`의 `lh.targetAreas`에 `{ "name": "고양창릉", "keywords": ["고양창릉", "창릉"] }`처럼 넣습니다. 단어는 공백 없이 적어도 `하남 교산`처럼 띄어 쓴 이름과 맞습니다. 고양창릉, 부천대장, 인천계양, 남양주 진접2 등은 일부러 넣지 않았습니다. 짧은 단어(`교산`, `토평`, `왕숙`)는 다른 공고 이름에도 걸릴 수 있습니다.
- **처리:** 뺀 공고는 판별, 저장, 알림을 하지 않습니다. 저장된 LH 행(`고유 키`가 `LH-`로 시작하거나 `소스`가 `LH`)은 일반 실행마다 알림 뒤에 Notion 휴지통으로 옮깁니다. 이번 실행에 빠진 공고의 행과, 이번 실행에 수집되지 않았고 저장된 `유형`·`주택명`·`공급지역`으로 범위 밖인 행이 대상입니다. 이번 실행에 수집되어 남은 공고의 행은 저장된 값으로 다시 보지 않고 그대로 갱신합니다. 저장된 `공급지역`이 비었거나 이름이 없는 행은 판정할 수 없어 지역으로는 옮기지 않습니다. 임대 정리와 달리 **`관심`을 체크한 행은 옮기지 않고**, 그 공고도 보통 공고처럼 갱신하고 알립니다. 실패하면 오류 메일에 `lh_out_of_scope_archive_failed`가 남고 잡은 실패로 끝나지만 알림은 이미 나간 뒤입니다.
- **로그:** `collected` 줄의 `lh_out_of_scope_skipped`(뺀 공고 수, 사유별 `lh_out_of_scope_type`, `lh_out_of_scope_area`), `lh_out_of_scope_archived`(옮긴 행 수), `lh_out_of_scope_kept_interest`(관심 체크로 남긴 행 수), `lh_type_unknown`(모르는 유형이라 남긴 공고 수), `lh_region_unknown`(공급지역이 비어 남긴 분양 공고 수)입니다. 공고 이름은 남기지 않습니다. dry-run은 옮기지 않고 `lh_out_of_scope_archive_candidates`로 건수만 남깁니다.
- **유형 값 확인(`lh_types`):** 실행마다 `lh_types 분양주택/공공분양=3,임대주택/국민임대=20`처럼 LH 원본 행의 `상위 유형/세부 유형`별 건수를 한 줄 남깁니다. 많은 순으로 30개까지이고, 한글·영문·숫자·`/`·`·`만 남기며 각 값은 20자에서 자릅니다. 빈 값은 `-`, LH 조회가 없으면 `none`입니다. 분류 이름이라 공개 로그에 남겨도 되며 공고 이름은 넣지 않습니다.
- **지역 값 확인(`lh_sale_regions`):** 실행마다 `lh_sale_regions 서울=2,경기=15`처럼 유형 규칙을 통과한(분양으로 남은, 유형이 비었거나 모르는 값 포함) LH 공고의 공급지역별 건수를 한 줄 남깁니다. 지역 규칙 전의 건수이고, 빈 공급지역은 `-`입니다. 글자 제한과 30개 상한은 `lh_types`와 같습니다.
- **유형 값:** 2026-11 실행에서 본 값은 `분양주택/분양주택`, `공공분양신혼희망/공공분양신혼희망`, `공공분양신혼희망/행복주택신혼희망`, `토지/토지`, `상가/…`, `임대주택/…`, `주거복지/매입임대`이고 `lh_type_unknown=0`이었습니다. 새 값이 생기면 `lh_types` 줄로 보고, `lh_type_unknown`이 0이 아니거나 `lh_out_of_scope_type`이 예상보다 크면 `lh.saleTypes`, `lh.nonSaleTypes`, `lh.excludeKeywords`를 고치세요. `lh.filterSaleArea`를 `false`로 두면 LH 공고를 예전처럼 저장합니다.

**쓰지 않는 열:** 배치는 `모집공고일`과 `순번`을 더 이상 쓰거나 읽거나 추가하지 않습니다(2026-11-09). 이미 있는 DB에서는 두 열을 지워도 되고, 남겨 두면 값이 갱신되지 않습니다. 새 DB에는 만들지 않습니다. 청약홈 수집 기간(`lookbackDays`)은 지금처럼 모집공고일 값으로 거릅니다. `접수 시작일`과 `접수 종료일`은 계속 씁니다.

**가정:** 신혼희망타운 유형 코드 `houseSecd === '10'`은 코드의 라벨 표(`src/sources/applyhome.js`)를 근거로 한 가정이며 실응답으로 확인되지 않았습니다.

## 11. 추천 전형

공고마다 지원할 전형과 그 접수일을 `추천 전형`, `추천 접수일` 열에 적고, 판별 근거 끝에 `추천: 신혼부부 특별공급 11/9 (30세대, 1순위 기타지역 11/11도 가능; 세대주·청약통장 요건 확인)`처럼 한 줄을 붙입니다. 두 열은 없을 때만 추가합니다.

`추천 전형`은 짧은 이름입니다. 특별공급은 `특별(신생아)`, `특별(신혼부부)`, `특별(생애최초)`, 일반 1순위는 거주 구분과 관계없이 `1순위`, 무순위·잔여세대는 `무순위`, 불법행위 재공급은 `재공급`, 임의공급은 `임의공급`입니다. 해당지역, 기타경기, 기타지역 구분은 판별 근거의 `추천:` 줄에만 적습니다. `추천 접수일`은 고른 단계의 접수 기간이고, 마감일이 시작일보다 늦으면 시작~마감 범위로 적습니다. 예전 이름(`신혼부부 특별공급`, `1순위 해당지역` 등)으로 저장된 행은 다음 판별 때 새 이름으로 바뀝니다. Notion 선택지 목록에 남은 예전 이름은 지우지 않아도 됩니다.

**신청자 정보:** 공개 저장소라 GitHub Secret `CHUNGYAK_PROFILE`에 한 줄 JSON으로 넣습니다. 워크플로가 배치 단계에만 넘기고, 배치는 값을 줄마다 `::add-mask::`로 가립니다(가림 명령은 한 줄만 받아, 여러 줄 값을 한 번에 넘기면 둘째 줄부터 로그에 찍히기 때문입니다. 괄호만 있는 줄은 가리지 않습니다). 배치는 이 값을 로그, 메일, Notion 어디에도 적지 않습니다.

```json
{"residenceSido":"인천","residenceYears":3,"specialTracks":["생애최초"]}
```

- `residenceSido`: 거주 시도(`서울`, `경기`, `인천` 등 공급지역 이름과 같은 표기). `인천광역시`처럼 쓰면 어떤 공고도 지역 대상이 되지 않아 추천이 비고, 지역 때문에 빼는 공고도 없습니다.
- `residenceYears`: 그 시도 거주 연수(0 이상의 숫자)
- `specialTracks`: 지원할 수 있는 특별공급. `신생아`, `신혼부부`, `생애최초`만 받습니다. 생략하면 특별공급을 추천하지 않습니다.

값이 없거나 형식이 틀리면 추천을 끄고 오류 메일 없이 로그 `recommend profile=missing` 또는 `profile=invalid`만 남깁니다. 이때 추천 열은 건드리지 않고 관심 알림은 저장된 추천 접수일, 없으면 접수 시작일로 보냅니다. 로그의 `recommend` 줄에는 추천한 공고 수와 추천이 없는 공고 수만 남습니다.

### 신청자 여러 명(v2)

각자 따로 청약하는 신청자가 여럿이면(예: 각자 1인 무주택 세대주인 두 사람) v2 형식을 씁니다. v2의 신청자는 한 세대나 한 커플이라고 보고, `household`의 혼인 정보를 모든 신청자에게 똑같이 적용합니다. 서로 다른 세대를 한 프로필에 넣으면 신혼부부와 가점 판단이 틀립니다. 위 v1 형식도 그대로 받고, v1의 추천과 판별 근거는 예전과 글자까지 같습니다. 아래 값은 모두 가짜 예시입니다.

```json
{
  "applicants": [
    {
      "label": "신청자A",
      "birthYear": 1990,
      "residenceSido": "인천",
      "residenceYears": 3,
      "account": { "joined": "2019-03", "payments": 40, "depositManwon": 350 },
      "specialTracks": ["생애최초"]
    },
    {
      "label": "신청자B",
      "birthYear": 1995,
      "residenceSido": "인천",
      "residenceYears": 3,
      "account": { "joined": null, "payments": null, "depositManwon": 200 },
      "specialTracks": ["신생아", "생애최초"],
      "pregnant": true,
      "childBirths": []
    }
  ],
  "household": { "married": false, "marriageRegistered": null }
}
```

- `applicants`: 신청자 1~4명. 순서가 추천 동점 처리 순서입니다.
- `label`: 6자 이하의 짧은 이름표(필수, 신청자끼리 달라야 함). 공백, 쉼표, `;`, `/`, `·`는 판별 근거의 구분자라 쓸 수 없습니다. `추천 전형` 열과 판별 근거에만 쓰고 로그에는 남기지 않습니다. 실명 대신 `A`, `B` 같은 별칭을 권합니다.
- `birthYear`: 출생 연도(정수). 가점 추정의 만 30세 계산에만 씁니다.
- `residenceSido`: v1과 같지만 v2는 짧은 시도 이름(`서울`, `부산`, `경기`, `세종` 등 17개)만 받고, `인천광역시`처럼 쓰면 형식 오류입니다.
- `residenceYears`, `specialTracks`: v1과 같고 신청자마다 따로 봅니다.
- `account`: 청약통장(필수). `joined`(가입 연월 `YYYY-MM`), `payments`(납입 횟수, 0 이상의 정수), `depositManwon`(예치금, 만원). 모르면 `null`로 두고, 모두 모르면 `"account": null`로 둡니다. 모르는 값은 막지 않고 판별 근거에 `확인:`으로 적습니다.
- `pregnant`: 임신 중이면 `true`(생략하면 `false`). `childBirths`: 자녀 출생 연월(`YYYY-MM`) 배열(생략하면 빈 배열).
- `household.married`: 혼인 여부(필수, `true`/`false`). `household.marriageRegistered`: 혼인신고일(`YYYY-MM-DD`) 또는 `null`. `married`가 `false`인데 신고일이 있으면 형식 오류입니다.

모르는 키가 있으면(예: `pregnent` 오타) 조용히 무시하지 않고 형식 오류(`profile=invalid`)로 추천을 끕니다. v2가 맞게 읽히면 로그의 `recommend` 줄 끝에 `version=2 applicants=2`처럼 신청자 수만 붙습니다.

**v2 규칙:** 숫자 기준(예치금 표, 가점 규칙, 특별공급 기간)은 규정을 요약한 것이라 틀리거나 바뀔 수 있습니다. 반드시 공고문과 청약홈으로 확인하세요.

1. **특별공급 시점 요건:** 기준일은 청약홈 모집공고일(`RCRIT_PBLANC_DE`)입니다. 확실히 아닐 때만 빼고, 애매하면 남긴 채 `확인:`에 적습니다.
   - `신생아`: 임신 중이면 씁니다. 아니면 공고월로부터 24개월 안(월 단위)에 태어난 자녀가 있을 때만 쓰고, 자녀가 없으면 뺍니다.
   - `신혼부부`: 혼인했고(`married: true`) 혼인신고일이 공고일 전 7년 안이면 씁니다. 7년이 지났으면 뺍니다. 혼인했는데 신고일이 `null`이면 남기고 `혼인신고일` 확인을 적습니다.
   - 미혼(`married: false`)의 `신혼부부`는 공고에 따라 다릅니다. 민영 공고는 혼인신고한 신혼부부만 받아 뺍니다. 국민·공공 공고(구분을 모르는 공고 포함)는 예비신혼부부(공고일 뒤 혼인 예정)와 6세 이하 자녀를 둔 한부모도 받으므로 남기고 `예비신혼부부 여부` 확인을 적습니다.
   - 공고일이 없으면 실행일로 기간을 재지 않습니다. 신생아 24개월과 신혼부부 7년을 보지 않고 남긴 채 `공고일` 확인을 적습니다(가점은 실행일로 추정합니다).
   - `생애최초`는 적힌 대로 씁니다(다른 요건은 확인 문구가 대신합니다).
2. **민영 예치금:** 청약홈 `HOUSE_DTL_SECD_NM`(없으면 `HOUSE_DTL_SECD`)로 민영 APT 공고를 가립니다(`docs/sources.md`). 민영 공고에서 신청자의 예치금이 공고의 가장 작은 주택형 전용면적 기준보다 적으면 그 신청자는 민영 1순위도 민영 특별공급도 추천하지 않고 `신청자B 예치금 60만 부족`처럼 적습니다. 기준은 신청자 거주지별입니다(만원, `config.json`의 `recommendation.privateDeposit`).

   | 거주지 | 85㎡ 이하 | 102㎡ 이하 | 135㎡ 이하 | 그 외 |
   |---|---|---|---|---|
   | 서울·부산 | 300 | 600 | 1000 | 1500 |
   | 기타 광역시(대구·인천·광주·대전·울산) | 250 | 400 | 700 | 1000 |
   | 기타 시·군(경기, 세종 포함) | 200 | 300 | 400 | 500 |

   주택형 면적을 모르거나(조회 실패, 알림 지역 밖, 값이 하나라도 빔) 예치금이 `null`이면 막지 않고 `확인: 신청자A 예치금(면적 미상)`처럼 적습니다. 국민주택이나 구분을 모르는 공고는 예치금을 보지 않고, 국민 공고에서 납입 횟수를 모르면 `납입횟수` 확인을 적습니다. 가입 월을 모르면 `통장 가입일` 확인을 적습니다.

   **통장 가입 기간과 납입 횟수:** APT 공고에서 아는 값만 쓰고, 확실한 것만 막습니다. 무순위·재공급·임의공급은 보지 않습니다.
   - 공고일에 가입 6개월 미만이면 그 신청자는 특별공급도 1순위도 추천하지 않고 `신청자A 통장 6개월 미만`이라고 적습니다.
   - 국민 공고에서 납입 6회 미만이면 특별공급만 빼고 `납입 6회 미만(특별공급 제외)`이라고 적습니다. 1순위는 남깁니다.
   - 1순위를 추천할 때 가입 기간이 수도권(서울·경기·인천) 공고면 24개월, 그 밖이면 12개월 미만일 때 `통장 가입기간` 확인을 적습니다. 수도권은 규제지역 여부에 따라 12개월 또는 24개월인데, 규제지역을 따지지 않고 24개월 미만이면 모두 적습니다. 국민 공고에서 납입 12회 미만이면 `납입 12회 미만` 확인을 적습니다.
3. **지역과 거주 구분:** v1 규칙을 신청자마다 그 신청자의 거주 시도와 연수로 적용합니다.
4. **공고 하나의 추천:** 신청자마다 v1과 같은 방식으로 추천을 고른 뒤, 접수일이 가장 이른 신청자를 고릅니다. 같으면 특별공급을 1순위보다 먼저, 특별공급끼리는 신생아, 신혼부부, 생애최초 순서, 그래도 같으면 `applicants` 순서입니다. `추천 전형`은 `신청자B 특별(신생아)`처럼 이름표와 짧은 이름이고(쉼표는 공백으로 바뀜), `추천 접수일`은 고른 신청자의 날짜입니다. 관심 알림도 `[관심 청약] … 신청자B 특별(신생아) 오늘 접수`처럼 이 값을 씁니다.
5. **판별 근거:** 신청할 수 있는 신청자를 모두 적습니다. 예: `추천: 신청자A 1순위 해당지역 11/10 (가점 약 28점) / 신청자B 신생아 특별공급 11/9 (30세대, 1순위 해당지역 11/10도 가능, 가점 약 9점(통장 제외)); 확인: 신청자B 통장 가입일; 세대주·청약통장 요건 확인; 가점은 추정`. 같은 내용(예: 무순위)은 `신청자A·신청자B 무순위 11/12`로 묶습니다. 통장·예치금 때문에 아무도 신청할 수 없으면 추천 열은 비우고 `추천 없음; 신청자B 예치금 60만 부족`처럼 까닭만 적습니다. 카카오톡의 짧은 근거에는 추천 문구를 넣지 않습니다.
6. **가점 추정:** 민영 또는 구분을 모르는 APT 공고에서 신청자마다 `가점 약 N점`을 적습니다(국민 공고는 가점제가 아니라 적지 않습니다). 기준일은 1번과 같고, 공고일이 없으면 실행일입니다. 추정치일 뿐이고 실제보다 높게 나오는 쪽입니다. 만 30세를 출생 연도+30년 1월 1일로 당기고, 통장 가입과 자녀 출생을 월 단위(그달 1일)로 세기 때문입니다.
   - 무주택 기간(최대 32점): 만 30세부터, 그 전에 혼인신고를 했으면 혼인신고일부터 셉니다. 혼인했는데 신고일을 모르면 30세부터 셉니다. 미혼이고 30세 전이면 0점, 1년 미만 2점, 이후 1년마다 2점.
   - 부양가족(최대 35점): 배우자(혼인했고 신고일이 공고일 뒤가 아님)와 이미 태어난 자녀만 셉니다(태아 제외). 5점 + 1명마다 5점.
   - 통장 가입 기간(최대 17점): 6개월 미만 1점, 1년 미만 2점, 이후 2점 + 다 채운 해 수. 가입 월을 모르면 빼고 `(통장 제외)`를 붙입니다.
7. **신청할 수 없는 공고:** 아래 규칙을 신청자마다 적용해, 모든 신청자에게 신청할 수 없을 때만 뺍니다. 모두 지역 때문이면 `region`, 아니면 `ended`로 셉니다. 통장·예치금 부족과 특별공급 시점 요건으로는 빼지 않습니다(2순위나 공고문 확인이 남기 때문입니다).

**Secret 바꾸기:** 저장소 루트에서 `gh secret set CHUNGYAK_PROFILE`을 실행하고 프롬프트에 한 줄 JSON을 붙여 넣습니다. 파일에 적어 두었다면 `gh secret set CHUNGYAK_PROFILE < profile.json`처럼 넣고, 그 파일은 저장소 밖에 두거나 넣은 뒤 지웁니다. 명령줄 인자(`--body`)로 넘기면 셸 기록에 남으므로 쓰지 않습니다. 바꾼 뒤에는 일반 실행 전에 dry-run으로 `recommend profile=ok`와 `unapplicable_*` 건수를 먼저 확인하세요.

**규칙:**

1. **APT 특별공급:** 신청자의 특별공급 중 이번 공고 주택형들에 세대가 있는 것을 고르고, 세대가 가장 많은 것, 같으면 신생아, 신혼부부, 생애최초 순으로 고릅니다. 날짜는 특별공급 접수 시작일입니다. 같은 공고에 특별공급 하나와 일반공급 하나를 함께 넣을 수 있어, 해당하는 일반 1순위 날짜도 함께 적습니다.
2. **APT 일반 1순위:** 맞는 특별공급이 없으면 일반 1순위입니다. 공고의 공급지역이 거주 시도와 같고 거주 연수가 `recommendation.localResidenceYears`(2년, 판단이 들어간 시작값) 이상이면 해당지역, 아니면 기타지역 날짜입니다. 경기 공고의 해당지역은 시·군 단위라 같은 시·군인지 알 수 없어, 경기 거주자에게는 기타경기 날짜를 추천하고 같은 시·군이면 해당지역이라고 적습니다. 다른 시도 거주자의 수도권 공고는 기타지역입니다. 고른 구분의 접수일이 공고에 없으면 추천하지 않습니다.
3. **무순위·잔여세대, 불법행위 재공급, 임의공급:** 그 접수일을 `무순위`, `재공급`, `임의공급`으로 추천합니다. 판별 근거에는 `추천: 불법행위 재공급 11/12`처럼 원래 이름을 적습니다.
4. **추천하지 않음:** 수도권 공고는 수도권 거주자, 그 밖은 같은 시도 거주자만 대상으로 보며 그 밖의 공고, 토지임대부·지분적립형·신혼희망타운, LH 공고와 오피스텔·도시형·민간임대 등은 추천하지 않고 열을 비웁니다. 세종(행복도시) 공고는 기타지역 1순위가 전국이라 어느 시도 거주자든 대상으로 보고, 세종 거주자가 아니면 기타지역(`1순위 기타`, `GNRL_RNK1_ETC_AREA`) 날짜를 추천합니다.
5. **접수가 끝난 단계:** 실행일(KST) 기준으로 접수 마감일이 지난 단계는 고르지 않습니다. 마감일이 없거나 시작일보다 이르면(잘못된 자료) 시작일 하루 접수로 봅니다. 특별공급, 일반 1순위 순으로 아직 접수할 수 있는 첫 단계를 추천하고, 다른 하나도 아직 열려 있으면 `…도 가능`으로 적습니다. 예를 들어 특별공급 11/9, 1순위 11/10인 공고는 11/10 실행에서 1순위로 바뀌고 그날 관심 알림이 갑니다. 11/9에 특별공급으로 관심 알림을 받았다면 11/10에 한 번 더 받습니다. 모든 단계가 끝났으면 추천하지 않고 열을 비웁니다.
6. **주택형 조회 실패:** APT 주택형 조회가 실패하면 특별공급 세대를 알 수 없으므로 다시 계산하지 않고 저장된 추천을 그대로 두며, 판별 근거 끝에 `(추천: 조회 실패로 이전 값 유지)`라고 적습니다. 실행마다 추천이 바뀌지 않게 하려는 것입니다.

**신청할 수 없는 공고 제외:** 신청자 정보가 있으면 Notion에는 아직 신청할 수 있는 공고만 남깁니다. 판단은 `src/recommend.js`의 `unapplicableReason`이고 추천과 같은 지역·단계 규칙을 씁니다.

- **빼는 공고:** (1) **지역:** 거주 시도가 수도권(서울·경기·인천)인 신청자에게, 수도권 밖이고 세종이 아닌 APT 공고만 지역 때문에 뺍니다. 수도권 밖 거주자는 1순위 기타지역이 광역 권역(예: 부산·울산·경남)을 따라 달라 지역으로 빼지 않습니다. 무순위·재공급은 정해진 1순위 거주 요건이 없고 임의공급은 거주 요건이 없어 지역으로 빼지 않습니다. 위 4번의 추천 지역 규칙은 그대로라, 지역으로 빼지 않은 공고도 추천은 비어 있을 수 있습니다. (2) **접수 종료:** APT·무순위·재공급·임의공급 중 위 4번 규칙으로 지역 대상인 공고에서 배치가 추천할 수 있는 전형의 접수가 모두 끝난 공고입니다. APT는 거주 구분에 맞는 일반 1순위가 끝났고, 신청자의 특별공급 세대가 있으면 특별공급도 끝났을 때입니다. 공고가 거주 시도에 있으면 실제 거주 구분이 추정과 다를 수 있어(공고마다 다른 거주 기간 요건, 경기의 같은 시·군) 1순위 해당·경기·기타가 모두 끝나야 뺍니다. 2순위가 남아 있어도 뺍니다. 무순위·재공급·임의공급은 본 접수일(`SUBSCRPT_RCEPT`)이 끝났고 다른 단계도 열려 있지 않을 때입니다. 본 접수일 없이 특별공급·일반공급 접수일만 있으면 빼지 않습니다.
- **빼지 않는 공고:** 신청자 정보가 없거나 형식이 틀리면 아무것도 빼지 않습니다. 토지임대부·지분적립형·신혼희망타운, LH 공고, 오피스텔·도시형 등 추천을 계산하지 않는 공고도 그대로 둡니다. 필요한 단계가 없거나 시작일·마감일이 비었거나 어긋나면, 주택형 조회가 실패하거나 세대 값이 비어 특별공급 세대를 모르면, 공급지역이나 거주 시도가 짧은 시도 이름(`서울`, `부산`, `세종` 등)이 아니면 빼지 않습니다. 판별 중 오류가 나면(`판별 불가`) 빼지 않고 저장합니다. 잘못된 자료로 지우지 않으려는 것입니다.
- **처리:** 새 공고는 저장하지 않고, 로또 긴급 알림과 주간 메일에도 넣지 않습니다. 이미 저장된 행은 일반 실행마다 알림 뒤에 Notion 휴지통으로 옮깁니다(영구 삭제가 아니라 30일 안에 되살릴 수 있습니다). `관심`을 체크한 행은 옮기지 않고 보통 공고처럼 갱신하며 로또 긴급 알림, 주간 메일, 관심 알림이 모두 그대로 갑니다. 접수가 끝나면 주간 정리가 옮깁니다. 관심 여부는 실행 시작 때 읽은 값이라, 실행 도중에 체크한 행은 그 실행에서 옮겨질 수 있습니다(휴지통에서 되살린 뒤 다시 체크하세요). Notion을 읽지 못한 실행은 관심 여부를 몰라 관심 행의 공고도 빼지만, 이때는 저장과 옮기기를 하지 않습니다. 이번 실행에 수집되지 않은 공고의 행과 접수 종료일이 이미 지난 행은 건드리지 않고, 그런 행은 접수 종료 정리가 옮깁니다.
- **로그:** `collected` 줄의 `unapplicable_skipped`(뺀 공고 수, 사유별 `unapplicable_region`, `unapplicable_ended`), `unapplicable_archived`(옮긴 행 수), `unapplicable_kept_interest`(관심 체크로 남긴 행 수)입니다. 공고 이름과 신청자 정보는 남기지 않습니다. 옮기기가 실패하면 오류 메일에 `unapplicable_archive_failed`가 남고 잡은 실패로 끝나지만 알림은 이미 나간 뒤입니다. dry-run은 옮기지 않고 `unapplicable_archive_candidates`로 건수만 남깁니다.

**한계:** 소득, 자산, 세대주, 무주택, 재당첨 제한은 보지 않습니다. 청약통장(가입 기간, 납입, 예치금)과 혼인·출산 시점 요건은 v2 신청자 정보가 있을 때 위 v2 규칙만큼만 대략 보고, v1에서는 보지 않습니다. 해당지역의 실제 거주 기간 요건도 공고마다 다릅니다. 추천은 데이터로 고른 출발점일 뿐이므로 공고문으로 반드시 확인하세요. 특별공급 유형별 세대수는 APT 주택형 자료에만 있어, 무순위 등에서는 특별공급을 고르지 않습니다.
